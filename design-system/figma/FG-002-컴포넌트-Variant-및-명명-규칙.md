# FG-002 컴포넌트·Variant 및 명명 규칙

> **핵심 결론:** Primitives → Patterns → Screens 계층을 사용한다. 시각 상태는 Variant, 변경 콘텐츠는 Component Property, 복잡한 상태는 Pattern으로 관리한다. 같은 역할과 구조가 3회 반복되거나 근거 있는 재사용 계획이 있으면 컴포넌트화한다.

- 문서 상태: 통합 반영용 초안
- 관련 승인: Q11~Q13, Q16~Q17, Q21~Q23

## 1. 계층 구조

| 계층 | 역할 | 예시 |
|---|---|---|
| Primitive | 시각 및 인터랙션 기본 요소 | `Primitive/Button`, `Primitive/Input` |
| Pattern | 여러 Primitive를 결합한 공통 기능 | `Species/PriceCard`, `Chat/MessageBubble`, `Chart/PeriodSelector` |
| Screen | 화면과 상태의 컴포지션 | `SCR-001`, `SCR-002`, `OVL-CHAT` |

Screen은 가능한 한 공통 컴포넌트 인스턴스를 사용하며 공통 스타일을 복제하지 않는다.

## 2. 승격 판단

1. 같은 화면의 반복 사용도 사용 횟수에 포함한다.
2. 구조와 역할이 실질적으로 같아야 같은 객체로 센다. 겉모양만 비슷한 객체는 합산하지 않는다.
3. **3회 이상 사용**되면 재사용 컴포넌트로 승격을 검토한다.
4. 현재 3회 미만이라도 **PRD·PF·UX에 재사용 위치가 명확하면** 승격을 검토한다.
5. 단순 장식 등 재사용 근거가 없는 요소는 일반 레이어로 유지할 수 있다.

## 3. Variant와 Property

- 시각적으로 구별해야 하는 상태 또는 유형은 Variant로 관리한다.
- 문구·아이콘 표시 여부·교체 가능한 콘텐츠는 적절한 Component Property로 관리한다.
- 재연결·로딩·조회 오류처럼 여러 요소와 시퀀스가 관련된 상태는 Pattern과 화면 상태를 결합한다.
- 가능한 모든 조합을 기계적으로 만들지 않고, **사용 중이거나 확정된 사용 예정 조합만** 우선 만든다.
- 조합 폭증 시 속성 구조 또는 하위 컴포넌트로 분리해 관리한다.
- 재사용 객체에 따른 승격과 개별 Variant의 개수는 서로 다른 문제이며 동일시하지 않는다.

## 4. 명명·참조 규칙

- Figma 컴포넌트: 영문 PascalCase 계층형, 예: `Chart/PeriodSelector`, `Chat/MessageBubble`.
- 컴포넌트의 역할·설명: 한글.
- 화면 및 상태 프레임: 원본 `SCR-*`·`ST-*` ID를 포함한다.
- 인터랙션은 해당 `UF-*`, `UX-D*`, `FR-*`에 연결한다.
- 기존 식별자를 임의로 새로 발급하거나 기존 정책 ID를 대체하지 않는다.

## 5. 인스턴스 사용과 변경

- 인스턴스의 콘텐츠와 공개된 Component Property 변경은 허용한다.
- 예외적인 스타일 Override는 **사유 기록 후** 허용한다. 기준은 `FV-002`를 따른다.
- 구조가 반복적으로 다른 경우 기존 인스턴스 편집을 누적하는 대신 새 Variant 또는 Pattern 승격을 검토한다.
- Main Component 변경 시 해당 컴포넌트의 모든 영향 화면·Variant·상태를 확인한다. 전역 토큰 변경은 전체 검증한다(Q17).
