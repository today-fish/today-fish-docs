# Docs Consistency Check

이 Skill은 docs repository의 문서 일관성을 지속적으로 유지하기 위한 증분 검사 workflow다.

매 실행마다 repository 전체를 다시 분석하지 않는다.

이전 검사 이후 추가·수정·삭제·이동된 문서를 우선 확인하고, 해당 변경의 정합성을 판단하는 데 필요한 기존 문서만 선택적으로 추가 확인한다.

이 repository는 프로젝트의 기획, 사용자 리서치, 제품 의사결정, 기술 설계 및 개발 기준을 관리하는 Source of Truth로 사용한다.

---

# 1. 핵심 운영 원칙

항상 다음 원칙을 따른다.

1. 최초 검사를 제외하고 repository 전체를 무조건 다시 읽지 않는다.
2. Git 변경사항을 기준으로 검사 대상을 결정한다.
3. 변경 문서만으로 판단할 수 없는 경우 관련 기존 문서만 추가 확인한다.
4. 기존 문서에 존재하지 않는 제품 결정을 임의로 만들지 않는다.
5. 문서 간 충돌이나 판단이 필요한 문제가 발견되면 임의로 수정하지 않는다.
6. 정합성 문제 발견 시 사용자에게 내용을 보고하고 검토를 요청한다.
7. 사용자의 판단 또는 승인을 받은 뒤 수정하거나 다음 검사 단계로 진행한다.
8. 전체 repository 검사가 필요한 경우 반드시 사전에 사용자 승인을 받는다.
9. `INDEX.md`는 실제 repository 구조와 항상 일치시킨다.
10. `README.md`는 repository의 대표 진입점 역할을 유지한다.
11. 모든 검사 결과는 `DOCUMENT-CHECK-HISTORY.md`에 기록한다.
12. 검사 이력을 기록한 후 해당 시점을 다음 검사의 baseline으로 사용한다.
13. 사용량 정보를 확인할 수 있는 경우 검사 결과에 사용량을 표시한다.
14. 실제 사용량을 확인할 수 없는 경우 값을 추정하거나 생성하지 않는다.

# 2. 관리 파일 및 위치

repository root를 기준으로 다음 파일을 사용한다.

```text
<repository-root>/
├── README.md
├── INDEX.md
├── DOCUMENT-CHECK-HISTORY.md
├── AGENTS.md
├── .codex/
│   └── skills/
│       └── docs-consistency-check/
│           └── SKILL.md
└── ...
```

## `DOCUMENT-CHECK-HISTORY.md`

검사 이력 파일의 위치는 반드시 다음과 같다.

```text
<repository-root>/DOCUMENT-CHECK-HISTORY.md
```

이 파일은 다음 정보를 관리한다.

- 검사 일시
- 이전 baseline
- 검사 대상 commit 범위
- 추가·수정·삭제·이동된 문서
- 수행한 검사
- 자동 수정한 항목
- 사용자 판단이 필요했던 항목
- INDEX.md 동기화 결과
- README.md 동기화 결과
- 검사 완료 상태
- 다음 검사 기준 commit
- 확인 가능한 경우 사용량 정보

`.codex/skills/` 내부에 검사 이력을 저장하지 않는다.

`DOCUMENT-CHECK-HISTORY.md`는 프로젝트 문서 관리 이력이므로 repository root에서 관리한다.

---

# 3. 검사 시작

검사를 시작하면 먼저 다음 파일을 확인한다.

```text
<repository-root>/DOCUMENT-CHECK-HISTORY.md
<repository-root>/INDEX.md
<repository-root>/README.md
```

그 다음 Git 상태를 확인한다.

```sh
git status --short
git rev-parse HEAD
```

`DOCUMENT-CHECK-HISTORY.md`가 존재하면 가장 최근 검사 기록에서 다음 검사 기준 commit을 찾는다.

예:

```text
다음 검사 기준:
`ad742bd`
```

baseline이 존재하면 해당 commit 이후의 변경사항을 확인한다.

```sh
git diff --name-status <baseline>..HEAD
```

아직 commit되지 않은 변경사항도 함께 확인한다.

```sh
git diff --name-status
git diff --cached --name-status
```

---

# 4. 전체 검사 여부 판단

다음 경우 전체 repository 검사가 필요할 수 있다.

- `DOCUMENT-CHECK-HISTORY.md`가 존재하지 않음
- 유효한 baseline commit을 찾을 수 없음
- baseline commit이 Git history에 존재하지 않음
- repository 문서 구조가 대규모로 변경됨
- 문서 관리 규칙 자체가 크게 변경됨
- INDEX.md와 실제 repository 사이에 광범위한 불일치가 발견됨
- 사용자가 명시적으로 전체 검사를 요청함

## 중요: 전체 검사 전 사용자 승인

전체 검사가 필요하다고 판단하더라도 즉시 수행하지 않는다.

먼저 사용자에게 다음 내용을 보고한다.

```text
전체 문서 검사가 필요합니다.

사유:
- 기존 검사 baseline을 찾을 수 없습니다.

예상 검사 범위:
- 전체 Markdown 문서
- 파일명 규칙
- 디렉토리 구조
- 문서 H1/H2 구조
- 내부 링크
- INDEX.md
- README.md
- 문서 간 주요 정합성

전체 검사를 진행할까요?
```

사용자의 승인을 받은 경우에만 전체 검사를 수행한다.

사용자가 승인하지 않으면 전체 검사를 수행하지 않는다.

가능한 경우 현재 변경 문서를 대상으로 한 제한적 검사만 수행할 수 있는지 안내한다.

---

# 5. 증분 검사

정상적인 경우 전체 repository가 아니라 baseline 이후의 변경사항만 검사한다.

변경 유형을 다음과 같이 구분한다.

- `A`: 신규 문서
- `M`: 수정된 문서
- `D`: 삭제된 문서
- `R`: 파일명 변경 또는 이동

예:

```text
A MVP/product/PD-010-알림-정책.md
M MVP/product/PD-003-Price-Insight-정의.md
D MVP/research/user/UR-002-기존-리서치.md
R MVP/product/PD-004-old.md
  MVP/product/PD-004-사용자-탐색-흐름.md
```

변경 문서를 먼저 검사하고 필요한 기존 문서만 선택적으로 추가 확인한다.

---

# 6. 관련 기존 문서 탐색

변경 문서와 다음 관계가 있는 문서를 우선 확인한다.

- 변경 문서가 직접 링크하는 문서
- 변경 문서를 직접 참조하는 문서
- 같은 제품 기능을 정의하는 문서
- 동일한 프로젝트 용어를 정의하는 문서
- 상위 제품 의사결정 문서
- 관련 사용자 리서치
- 관련 기술 설계
- 동일 디렉토리에서 직접적인 관계가 있는 문서

관련성을 명확하게 설명할 수 없는 문서를 불필요하게 전체 탐색하지 않는다.

---

# 7. 검사 중 문제 발견 시 사용자 검토

검사 과정에서 정합성 문제, 충돌 또는 사용자의 제품 판단이 필요한 상황이 발견되면 해당 지점에서 임의로 수정하거나 다음 관련 작업을 계속하지 않는다.

먼저 사용자에게 문제를 보고한다.

예:

```text
문서 정합성 문제가 발견되었습니다.

변경 문서:
PD-010-알림-정책.md

관련 기존 문서:
PD-003-Price-Insight-정의.md

충돌:
- PD-003: 알림은 MVP 이후 기능
- PD-010: 알림을 MVP 필수 기능으로 정의

가능한 처리:
1. PD-003 기준 유지
2. PD-010 기준으로 기존 결정을 변경
3. 두 문서의 역할을 다시 구분
4. 현재 상태 유지 후 별도 의사결정

검토 후 처리 방향을 알려주세요.
```

사용자의 판단을 받은 뒤 수정 또는 다음 관련 작업을 수행한다.

## 검토 요청이 필요한 문제

다음은 반드시 사용자 검토를 요청한다.

- 서로 다른 Accepted decision의 충돌
- MVP 범위 변경
- 타깃 사용자 변경
- 핵심 제품 가치 변경
- Price Insight 정의 변경
- 데이터 기준 변경
- 기능 포함/제외 정책 변경
- Business Model 변경
- 주요 기술 설계 방향 변경
- 어떤 문서가 최신 기준인지 판단하기 어려운 경우
- 문서 삭제로 인해 중요한 근거가 사라지는 경우

---

# 8. 자동 수정 가능한 문제

제품 판단이 필요하지 않은 명백한 문제는 사용자 승인 없이 수정할 수 있다.

예:

- 잘못된 Markdown 링크
- 파일 이동에 따른 링크 경로 수정
- INDEX.md의 오래된 파일명
- 삭제된 문서의 INDEX 항목 제거
- 신규 문서 INDEX 등록
- H1/H2 변경사항을 INDEX에 반영
- 명백한 Markdown whitespace 문제
- 단순 오타
- 동일한 프로젝트 고유명사의 명백한 철자 오류

단, 자동 수정 결과는 최종 보고와 검사 이력에 반드시 기록한다.

---

# 9. 파일명 규칙 검사

문서 ID가 있는 Markdown 파일은 기존 repository 규칙을 따른다.

기본 형식:

```text
PREFIX-NNN-문서명.md
```

예:

```text
PD-001-타깃-사용자-정의.md
PD-003-Price-Insight-정의.md
UR-002-가격-탐색-행동-리서치.md
```

확인한다.

- prefix
- 문서 번호
- 번호 중복
- 한국어 중심 파일명
- 프로젝트 고유 영어 명사 유지
- `-` 기반 단어 구분
- 문서 내용과 파일명 일치
- 지나치게 길거나 모호한 이름

다음과 같은 프로젝트 고유명사는 임의 번역하지 않는다.

```text
오늘의 수산
Price Insight
MVP
API
Backend
Frontend
Redis
PostgreSQL
OAuth
AWS
```

---

# 10. 디렉토리 구조 검사

문서의 역할과 저장 위치가 일치하는지 확인한다.

예:

```text
MVP/product/
```

- 제품 정의
- 제품 전략
- 기능 정의
- 제품 의사결정

```text
MVP/research/user/
```

- 사용자 조사
- 사용자 행동
- 인터뷰
- 사용자 근거

새로운 문서의 위치가 명백하게 잘못된 경우 적절한 위치를 제안한다.

문서 이동이 다른 문서 구조 또는 제품 의미에 영향을 주는 경우 사용자 검토를 요청한다.

---

# 11. 문서 구조 검사

변경 문서에서 다음을 확인한다.

- H1 존재 여부
- 불필요한 다중 H1
- H2/H3 계층
- 문단 길이
- 핵심 결론 위치
- 상태 표현
- 확정 내용과 제안 내용의 구분
- 기존 문서 스타일과의 일관성
- 중복 설명 여부

문서 상태 체계가 존재한다면 `Draft`, `Proposed`, `Accepted`, `Deprecated` 등의 사용도 확인한다.

---

# 12. 프로젝트 용어 검사

같은 개념이 여러 표현으로 혼용되지 않는지 확인한다.

특히 다음을 확인한다.

- 제품명
- 기능명
- 핵심 제품 개념
- 사용자 유형
- 가격 기준
- 데이터 기준
- MVP 범위
- 시스템 구성요소

고유명사는 기존 표기를 우선한다.

---

# 13. 문서 간 정합성 검사

변경 문서가 기존 Source of Truth와 충돌하는지 확인한다.

중점 검사 대상:

- 문제 정의
- 타깃 사용자
- Positioning
- 제품 가치
- MVP 범위
- 기능 포함/제외
- Price Insight
- 사용자 흐름
- 데이터 출처
- 가격 기준
- Business Model
- Growth Strategy
- 기술 설계
- API
- 운영 정책

충돌이 발견되면 자동으로 어느 한쪽을 수정하지 않는다.

반드시 사용자 검토 절차를 수행한다.

---

# 14. INDEX.md 동기화

모든 일관성 검사에서 `INDEX.md`를 반드시 확인한다.

다음 변경은 INDEX에 반영한다.

- 신규 문서
- 삭제 문서
- 파일명 변경
- 문서 이동
- H1 변경
- 주요 H2 변경
- 문서 역할 변경
- 디렉토리 구조 변경

확인 항목:

1. 신규 문서가 등록되어 있는가
2. 삭제 문서가 남아 있지 않은가
3. 실제 파일명이 일치하는가
4. 실제 경로가 일치하는가
5. Markdown 링크가 정상인가
6. H1이 일치하는가
7. 주요 H2가 일치하는가
8. 디렉토리 구분이 올바른가
9. 중복 항목이 없는가
10. 문서 ID 순서가 자연스러운가

---

# 15. INDEX.md 증분 갱신

INDEX 전체를 매번 재작성하지 않는다.

변경된 문서가 포함된 부분만 갱신한다.

예:

```text
A MVP/product/PD-010-알림-정책.md
```

이면:

1. `MVP/product/` INDEX 영역 확인
2. 적절한 문서 ID 위치 확인
3. 문서 링크 추가
4. H1 확인
5. 주요 H2 추가
6. 필요한 경우 관련 문서 정보 갱신

다음 경우 전체 INDEX 검사가 필요할 수 있다.

- INDEX 자체가 광범위하게 손상됨
- repository와 INDEX가 대규모로 불일치
- 디렉토리 구조가 대규모 변경됨

이 경우에도 전체 INDEX 검사를 수행하기 전에 사용자 검토를 요청한다.

---

# 16. README.md 동기화

README는 repository의 대표 진입점이다.

다음을 유지한다.

- 프로젝트 소개
- repository 목적
- 주요 디렉토리
- 주요 문서 영역
- 추천 읽기 순서
- INDEX 또는 주요 문서 링크

모든 개별 문서를 README에 나열하지 않는다.

README에 영향을 주는 변경만 반영한다.

---

# 17. README와 INDEX 역할

## README.md

질문:

> 이 repository는 무엇이며 어떻게 읽어야 하는가?

에 답한다.

## INDEX.md

질문:

> 내가 찾는 정보는 어느 문서에 있는가?

에 답한다.

# 18. 검사 이력 기록

모든 검사 결과는 다음 위치에 기록한다.

```text
<repository-root>/DOCUMENT-CHECK-HISTORY.md
```

기존 이력을 삭제하거나 덮어쓰지 않는다.

새로운 검사 기록을 누적한다.

```md

- 내부 링크: 정상 / 자동 수정 / 검토 필요
- 문서 정합성: 정상 / 검토 필요 / 충돌
- INDEX.md: 정상 / 수정 / 검토 필요
- README.md: 정상 / 수정 / 검토 필요

- 수정 내용

없으면:

- 없음

### 사용자 검토

사용자 판단이 없었다면:

- 없음

사용자 판단이 있었다면:

- 발견된 문제
- 사용자 결정
- 반영 결과

### 확인된 문제

없으면:

- 없음

해결되지 않았다면 문제와 관련 문서를 기록한다.

또는:

`검토 필요`

`<commit hash>`
```

# 19. 사용량 표시

검사 시작과 완료 시 사용 가능한 usage 정보를 확인한다.

가능한 경우 다음을 표시한다.

```text
검사 시작 사용량
- 사용 가능량: ...
- 잔여량: ...

검사 완료 사용량
- 이번 검사에서 사용: ...
- 잔여량: ...
```

단, 정확한 사용량 또는 잔여량을 Codex 실행 환경에서 제공하지 않는 경우 절대로 임의 계산하지 않는다.

그 경우 다음과 같이 표시한다.

```text
검사 사용량
- 정확한 token 사용량: 확인 불가
- 잔여 token/사용량: 확인 불가
```

모델 내부 추정치나 대화 길이를 기반으로 실제 quota를 추정하지 않는다.

Codex가 제공하는 `/status` 또는 해당 실행 환경의 공식 usage 정보에 접근할 수 있는 경우 해당 값을 우선 사용한다.

token과 subscription usage가 서로 다른 개념이라면 혼용하지 않는다.

예:

```text
Token usage: 확인 가능 시 표시
Codex 5시간/주간 allowance: 확인 가능 시 별도 표시
```

# 20. 검사 중단 및 승인 checkpoint

다음 상황에서는 현재까지의 검사 결과를 유지한 채 사용자 입력을 요청한다.

### Checkpoint A — 전체 검사

전체 repository 검사가 필요한 경우.

### Checkpoint B — 문서 정합성 충돌

두 개 이상의 문서가 서로 다른 제품 결정을 정의하는 경우.

### Checkpoint C — 제품 결정 변경

기존 Accepted decision의 수정이 필요한 경우.

### Checkpoint D — 구조 변경

대규모 디렉토리 이동 또는 문서 분리가 필요한 경우.

### Checkpoint E — 판단 불가

어떤 문서가 최신 또는 최종 Source of Truth인지 판단할 근거가 부족한 경우.

Checkpoint에서는 문제를 최대한 구체적으로 설명하고 선택 가능한 처리 방향을 제시한다.

# 21. 검사 재개

사용자 검토 후 기존 검사 문맥을 이어서 진행한다.

이미 완료한 검사를 불필요하게 처음부터 다시 수행하지 않는다.

사용자가 결정한 내용은 이번 검사 결과와 `DOCUMENT-CHECK-HISTORY.md`에 기록한다.

# 22. Baseline 갱신

작업 순서는 다음과 같다.

```text
1. 이전 baseline 확인
2. Git 변경사항 탐색
3. 변경 문서 검사
4. 관련 문서 검사
5. 정합성 검사
6. 문제 발생 시 사용자 검토
7. 승인된 수정 적용
8. INDEX.md 동기화
9. 필요한 경우 README.md 동기화
10. 링크/Markdown 검증
11. DOCUMENT-CHECK-HISTORY.md 기록
12. 최종 검증
13. 현재 HEAD를 다음 baseline으로 기록
```

검사 도중 해결되지 않은 중요한 문제가 있으면 baseline 갱신을 보류한다.

history에는 다음과 같이 기록한다.

```text
검사 상태: 검토 필요
baseline 갱신: 보류
```

# 23. Git 검증

가능하면 다음 명령을 활용한다.

```sh
rg --files
git status
git diff --check
git diff --word-diff
```

필요한 경우:

```sh
git diff --name-status <baseline>..HEAD
git diff --cached --name-status
rg "검색 대상"
```

을 사용한다.

# 25. 핵심 목표

이 Skill의 최종 목표는 다음과 같다.

> docs repository가 하나의 프로젝트 문서 시스템으로 지속적으로 동작하도록 유지한다.

이를 위해:

- Git을 이용해 변경사항을 증분 추적하고
- 변경 문서와 필요한 관련 문서만 확인하며
- 제품 의사결정의 정합성을 검사하고
- 판단이 필요한 문제는 사용자에게 넘기며
- INDEX.md를 실제 repository와 동기화하고
- README.md를 프로젝트 진입점으로 유지하고
- 모든 검사 이력을 repository root의 `DOCUMENT-CHECK-HISTORY.md`에 남기며
- 다음 검사에서는 이전 검증 결과를 활용한다.

전체 검사는 예외적인 작업으로 취급하고 반드시 사용자 승인을 받은 후 수행한다.
