- **버전:** V1
- **상태:** 승인
- **기준일:** 2026-11-11
- **대상:** 오늘의 수산 백엔드 MVP
- **관련 문서:** [BE-ADR-001](../BE-ADR-001-백엔드-아키텍처.md), [BE-ADR-002](../BE-ADR-002-런타임-및-웹-프레임워크.md), [BE-ADR-005](../BE-ADR-005-데이터베이스-및-AWS-인프라.md), [FE-ADR-009](../../frontend/adr/FE-ADR-009-MVP-익명-사용자-식별-및-보안-토큰-관리-전략.md), [PF-005](../../../product/features/PF-005-실시간-채팅.md), [BE-TECH-SPEC-006](BE-TECH-SPEC-006-실시간-채팅.md), [통합 ERD](../erd/BE-ERD-001-통합-데이터-모델.md)

## Summary

회원가입 없는 익명 사용자에게 수산물별 실시간 채팅을 제공한다. 최초 채팅 인증 준비 시 `APP_USER`를 생성하고 HS256 서명 JWT를 HttpOnly 쿠키로 발급한다. 유효한 JWT를 가진 사용자는 재접속 시 동일하게 식별하며, 만료된 JWT로는 기존 사용자를 복원하지 않는다.

HTTP 인증은 Stateless로 운영한다. WebSocket 연결 시 JWT를 검증해 사용자 `Principal`을 설정하고, 연결 이후 JWT 만료만으로 기존 연결을 종료하지 않는다.

동일 사용자의 다중 탭·다중 WebSocket 연결을 허용한다. HTTP 세션, Redis, 영속 세션 저장소는 사용하지 않는다. **품목별 참여자 세션·닉네임·색상·3분 예약은 별개의 채팅 상태이며 006의 서버 메모리 관리 책임이다.**

## 1. 범위와 불변 조건

1. 사용자 식별자는 `APP_USER.id BIGINT`를 사용한다.
2. JWT는 HS256으로 서명하며 서버에서 검증한다.
3. JWT 유효기간은 30일, 갱신 구간은 만료 7일 전부터다.
4. 유효한 JWT의 사용자 ID가 실제 DB에 존재하는지 인증 준비 및 WebSocket 연결 시 확인한다.
5. 동일 사용자가 여러 WebSocket 연결을 가질 수 있다.
6. 연결·구독 상태 및 006의 품목별 참여자 상태는 Spring 서버 메모리에서 관리한다.
7. CSRF는 쿠키 기반 저장소와 STOMP CONNECT 검증을 사용한다.
8. 만료된 사용자 레코드는 삭제하지 않는다.

MVP 비목표는 회원가입·OAuth, Refresh Token, JWT 폐기 목록, 사용자 제재, 메시지 영구 저장·조회·삭제, DAU·MAU 집계다.

## 2. 데이터 모델

### 2.1 APP_USER

```sql
CREATE TABLE app_user (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

| 컬럼         | 설명                |
| ------------ | ------------------- |
| `id`         | 내부 익명 사용자 ID |
| `created_at` | 최초 생성 시각      |

BIGINT는 UUIDv4보다 작은 인덱스 크기와 순차 삽입 지역성을 제공한다. 단일 PostgreSQL 구조이므로 분산 ID 생성은 필요하지 않다.

닉네임, 세션, 활동 시각, 사용자 상태 컬럼은 추가하지 않는다.

`APP_USER`는 JWT 만료 후에도 보존한다. 쿠키 삭제·만료·최초 동시 발급으로 동일한 사람이 여러 ID를 가질 수 있다.

`created_at`으로 일별·월별 신규 익명 사용자 ID 수를 집계할 수 있지만 DAU·MAU는 계산할 수 없다. 전체 서비스 MAU는 향후 별도 분석 계약으로 처리한다.

### 2.2 ERD 변경

통합 ERD에 `APP_USER` 1개 테이블을 추가한다. 승인된 ERD V1 Baseline에 반영되어 있다.

세션·JWT·채팅 메시지 테이블은 추가하지 않는다. 현재 005가 기존 가격·수집 테이블에 추가하는 FK도 없다.

## 3. JWT 및 쿠키 정책

### 3.1 JWT 계약

| 항목     | 정책                     |
| -------- | ------------------------ |
| 알고리즘 | HS256                    |
| 서명키   | CSPRNG 기반 최소 256비트 |
| `iss`    | `today-fish`             |
| `aud`    | `today-fish-web`         |
| `sub`    | `APP_USER.id` 문자열     |
| `iat`    | 발급 시각                |
| `exp`    | 발급 후 30일             |

서버는 서명·허용 알고리즘·발급자·대상·발급 시각·만료 시각·사용자 ID 형식을 검증한다. 잘못된 토큰은 거부한다.

`jti`, 사용자 권한, 개인정보는 JWT에 저장하지 않는다.

서명키는 GitHub에 저장하지 않고 서버 환경 비밀값으로 주입한다. 긴급 키 교체 시 기존 JWT가 무효화될 수 있음을 허용한다.

### 3.2 갱신 정책

- JWT가 없거나 **정상 서명된 상태에서** 만료되면 새로운 `APP_USER`를 생성한다.
- 유효기간이 7일 초과 남았다면 기존 JWT를 유지한다.
- 7일 이하라면 동일 `sub`로 30일 JWT를 재발급한다.
- 서명이 잘못됐거나 Claim이 변조된 JWT는 자동 발급하지 않고 거부한다.
- 만료된 JWT를 이용한 기존 사용자 복원은 금지한다.
- 여러 탭의 동시 갱신을 허용하며 별도 락은 사용하지 않는다.
- Refresh Token을 발급하지 않는다.

### 3.3 쿠키 계약

```http
Set-Cookie: __Host-fish_auth=<JWT>; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=2592000
```

`Domain`은 설정하지 않는다. JWT는 JavaScript와 응답 본문에 노출하지 않는다.

브라우저는 대상 호스트와 쿠키 조건이 일치하는 요청에 JWT를 자동 전송한다. 공개 가격·Insight·이슈 조회에는 JWT 인증을 요구하지 않는다. 운영 프론트엔드와 API가 서로 다른 사이트이면 `SameSite=Lax` 쿠키가 fetch 또는 WebSocket에 전송된다고 가정하지 않는다. 실제 도메인의 사이트 관계와 브라우저 제한을 검증한다.

## 4. API 및 Java 계약

### 4.1 HTTP API

| 메서드 | 경로                  | 기능                           |
| ------ | --------------------- | ------------------------------ |
| GET    | `/api/auth/csrf`      | 인증 전에도 CSRF 토큰 제공     |
| POST   | `/api/auth/anonymous` | 익명 사용자 생성·검증·JWT 갱신 |

최초 채팅 FAB 클릭 후 인증 순서는 **GET CSRF → POST 익명 인증 → WebSocket 핸드셰이크 → STOMP CONNECT** 순서다. `GET /api/auth/csrf`는 사용자 레코드를 생성하지 않으며 `Cache-Control: no-store`를 적용한다.

`POST /api/auth/anonymous`는 CSRF 검증 후 처리한다.

| JWT 상태                 | 처리                       |
| ------------------------ | -------------------------- |
| 없음·정상 만료           | 새 사용자 생성 및 JWT 발급 |
| 유효·잔여 7일 초과       | 사용자 존재 확인 후 유지   |
| 유효·잔여 7일 이하       | 사용자 존재 확인 후 갱신   |
| 서명·Claim 오류          | 401                        |
| 유효 JWT의 사용자 미존재 | 401                        |

성공 응답은 `200 OK`와 `{"authenticated":true}`를 반환한다. 새 JWT가 필요한 경우에만 `Set-Cookie`를 설정한다.

### 4.2 Java 계약

```java
public record VerifiedJwt(
    Long userId,
    Instant issuedAt,
    Instant expiresAt
) {}

public interface JwtService {
    VerifiedJwt verify(String token);
    String issue(Long userId, Instant issuedAt);
}
```

```java
public record AuthResult(
    Long userId,
    String jwt,
    boolean cookieUpdateRequired
) {}

public interface AnonymousAuthService {
    AuthResult prepare(String existingJwt);
}
```

JWT 갱신이 불필요하면 `jwt`를 반환하지 않는다. 인증 실패는 유형별 예외로 구분한다.

`AppUserRepository`는 Spring Data JPA의 `save`, `existsById`를 우선 사용한다. 별도 인증 추상화 계층은 도입하지 않는다.

## 5. WebSocket 인증 및 세션

### 5.1 연결 인증

1. 브라우저가 유효한 JWT 쿠키로 WebSocket 핸드셰이크를 요청한다.
2. 서버가 Origin과 JWT를 검증한다.
3. `APP_USER` 존재를 확인한다.
4. 검증된 userId를 `Principal`에 설정한다.
5. STOMP CONNECT에서 CSRF를 검증한다.
6. 인증된 연결에 대해 006의 품목별 채팅 참여·구독 검증을 수행한다.

브라우저가 전송한 `userId`나 STOMP `login` 값을 신뢰하지 않는다.

### 5.2 연결 수명

JWT는 WebSocket 연결 시점에 검증한다.

연결 이후 JWT가 만료되더라도 기존 연결과 Principal을 유지한다. 새 연결이나 재연결은 해당 시점의 유효 JWT로 다시 인증한다.

### 5.3 다중 탭

```text
APP_USER #1001
├── WebSocket Session A → 갈치 구독
├── WebSocket Session B → 고등어 구독
└── WebSocket Session C → 전복 구독
```

하나의 사용자 ID에 여러 연결을 허용한다. WebSocket Session ID는 사용자 ID와 독립적이다. 탭 하나가 종료되어도 다른 연결에는 영향을 주지 않는다.

Spring STOMP Simple Broker가 연결·구독 정보를 관리한다. 별도 HTTP Session 또는 PostgreSQL 연결 이력 테이블을 생성하지 않는다.

### 5.4 품목별 참여자 세션과의 경계

**005의 JWT 사용자 ID와 006의 품목별 참여자 세션은 별개다.** 같은 사용자가 서로 다른 어종에서 다른 닉네임·색상을 사용할 수 있고, 같은 품목의 여러 탭이 하나의 참여자 세션을 공유할 수 있다.

006은 서버 메모리에서 참여자 세션의 소유자·품목·활성 연결 집합·닉네임/색상·3분 예약을 관리한다. 소유권 확인은 서버 발급 참여자 세션 ID, 검증된 Principal과 서버 보관 세션 상태를 사용하며 `localStorage`의 식별자만 신뢰하지 않는다. 별도 복원 토큰은 발급하지 않는다.

동일 JWT 사용자 ID를 사용하는 연결은 006에서 사용자·품목별 세션을 공유한다. 최초 동시 발급으로 서로 다른 ID가 생성되면 같은 브라우저라도 다른 참여자가 될 수 있다. JWT 만료 또는 쿠키 삭제로 새 ID가 발급되면 기존 세션을 복원하지 않는다. 유효 JWT 또는 동일 ID로 갱신된 JWT는 006의 소유권·품목·예약 조건을 충족하면 복원할 수 있다.

## 6. CSRF·CORS·Origin 보안

### 6.1 CSRF

Spring Security의 `CookieCsrfTokenRepository`를 사용한다.

`GET /api/auth/csrf`는 익명 JWT 없이 요청할 수 있으며 요청에 사용할 토큰을 응답으로 제공한다.

```json
{
  "headerName": "X-XSRF-TOKEN",
  "token": "<csrf-token>"
}
```

토큰은 HTTP 인증 요청 헤더와 STOMP CONNECT native header로 전달한다.

- `POST /api/auth/anonymous`: HTTP CSRF 필수
- `STOMP CONNECT`: CSRF 필수
- CSRF 누락·불일치: 요청 또는 연결 거부
- JWT 갱신만으로 CSRF 토큰을 강제 교체하지 않음

HTTP 세션 없이 토큰을 저장·검증한다. Spring Security 7의 세션 없는 CSRF 저장·조회, 인증 전 발급, CSRF 쿠키와 React 메모리 전달, 동시 탭 쿠키 및 STOMP 연계는 구현 시 통합 검증한다.

### 6.2 CORS 및 Origin

HTTP CORS는 환경별 정확한 프론트엔드 Origin만 허용한다.

```text
Allowed Origins:
  운영: 배포 프론트엔드 Origin
  개발: 로컬 프론트엔드 Origin

Allow Credentials: true
Allowed Methods: GET, POST
Allowed Headers: Content-Type, X-XSRF-TOKEN
```

WebSocket은 별도의 Origin 허용 목록을 적용한다. Credential을 허용하는 API에서 와일드카드 Origin을 사용하지 않는다.

Origin은 JWT 인증을 대체하지 않는다.

## 7. 트랜잭션 및 동시성

### 7.1 최초 사용자 발급

```text
BEGIN
  APP_USER INSERT
  JWT 생성
COMMIT

Set-Cookie 응답
```

사용자 생성과 JWT 생성은 짧은 트랜잭션으로 처리한다. JWT 생성 실패 시 롤백한다. DB 커밋이 성공한 후에만 성공 응답을 작성한다.

커밋 후 HTTP 응답이 유실되면 사용되지 않는 사용자 레코드가 남을 수 있으며 이를 허용한다.

### 7.2 기존 사용자 및 갱신

기존 사용자 인증에서는 JWT 검증 후 `APP_USER` 존재만 조회한다. JWT 갱신은 DB 쓰기 트랜잭션을 요구하지 않는다.

여러 탭의 동시 최초 발급으로 복수 사용자 ID가 생성되는 것을 허용한다. 여러 탭의 동시 JWT 갱신도 허용하며 분산 락·세션 동기화 테이블은 도입하지 않는다.

동일 WebSocket 연결의 Principal은 연결 시점에 확정한 userId를 유지한다.

## 8. 오류 및 장애 대응

| 상황                    | 처리                             |
| ----------------------- | -------------------------------- |
| JWT 위조·Claim 오류     | HTTP 401 / 연결 거부             |
| JWT 정상 만료           | 인증 준비 API에서 새 사용자 발급 |
| 사용자 ID 미존재        | HTTP 401 / 연결 거부             |
| HTTP CSRF 실패          | 403                              |
| STOMP CONNECT CSRF 실패 | CONNECT 거부                     |
| 비허용 WebSocket Origin | 핸드셰이크 거부                  |
| APP_USER INSERT 실패    | 롤백, JWT 미발급                 |
| JWT 생성 실패           | 롤백                             |
| DB COMMIT 실패          | 정상 JWT 응답 금지               |
| DB 사용 불가            | 503                              |
| 내부 JWT 처리 장애      | 500                              |
| WebSocket 네트워크 장애 | 제한적 재연결                    |
| 연결 중 JWT 만료        | 연결 유지                        |

재연결 시 인증 준비 API로 JWT를 확인한 후 새로운 WebSocket 연결을 생성한다. 연결이 끊긴 동안 발생한 채팅 메시지는 복구하지 않는다.

인증 장애가 가격·Insight·이슈 공개 조회까지 전파되지 않도록 한다.

### 8.1 로그 및 운영

애플리케이션 로그에는 사용자 생성 실패, JWT 검증 오류 유형, CSRF 실패, WebSocket 인증 실패, DB 장애를 기록한다.

JWT 원문·서명키·CSRF 토큰·전체 쿠키 값은 기록하지 않는다.

별도 인증 이력 테이블과 사용자 정리 배치는 도입하지 않는다.

### 구현 전 확인

- Spring Security 7의 Stateless JWT 인증과 WebSocket Principal 전달
- CookieCsrfTokenRepository의 HTTP·STOMP CSRF 검증 호환성
- 다중 탭에서 JWT·CSRF 쿠키 공유 및 갱신
- JWT 발급 트랜잭션의 커밋·응답 순서
- 배포 도메인의 쿠키·CORS·Origin 정책
- 운영 도메인의 SameSite=Lax, __Host- 쿠키, credentials: include, CORS와 WebSocket Origin 및 브라우저의 교차 사이트 쿠키 전송

위 항목은 구현 검증·문서 동기화 대상으로 관리하며 승인된 기능 정책을 임의로 변경하지 않는다.
