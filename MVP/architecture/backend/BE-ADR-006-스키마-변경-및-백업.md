# BE-ADR-006 — DB 스키마 변경·백업 정책

- **상태:** 승인
- **결정:** 2026-10-29

## 핵심 결론

**Hibernate 자동 DDL은 모든 환경에서 `ddl-auto=none`으로 비활성화한다. MVP 개발 중에는 실험적 DDL을 자유롭게 관리하고, 운영 전환 시 최종 스키마를 Flyway `V1`으로 확정한다. 이후 변경은 Flyway 버전별 SQL로 관리한다.**

## 개발 단계

- MVP 개발 DB는 필요 시 재생성할 수 있다. 다만 현재 스키마 재구성 SQL·설명은 Git에 보관한다.
- 개발 중 실험적 변경을 매번 Flyway `Vn`으로 누적하지 않는다.
- 데이터 수집 PoC 결과 등 재확보가 불가능한 자료는 DB 초기화 전에 별도로 보존 여부를 판단한다.
- `ddl-auto=none` 유지. 엔티티와 실제 스키마 불일치는 개발·CI 검사에서 발견하도록 한다.

## 운영 전환

1. 최종 개발 스키마의 테이블·인덱스·제약·확장·타입 검토.
2. `V1__initial_schema.sql` 작성.
3. **빈 PostgreSQL 테스트 DB**에 `V1`만 적용해 스키마 전체 재구성 및 JPA 검증.
4. 비어 있는 운영 RDS에 `V1` 적용 후 애플리케이션 배포.
5. 운영 이후 적용된 Flyway 파일은 수정하지 않고 `V2`, `V3` 등으로 누적.

## 운영 정책

- 운영에서는 애플리케이션 기동 시 Flyway 자동 실행을 사용하지 않는다. **배포 파이프라인의 명시적인 마이그레이션 단계**에서 실행한다.
- 런타임 DB 계정과 마이그레이션용 DDL 계정 분리는 AWS 배포 방식에서 구체화한다.
- 변경은 기존 애플리케이션과의 호환성(Expand-Contract)을 우선한다.
- 파괴적 변경은 데이터 보존·복구와 배포 순서를 별도로 검토한다.
- 스키마 변경 이력은 Flyway+Git, 데이터 복구는 RDS 자동 백업·PITR로 **역할 분리**한다. `pg_dump --schema-only`는 현재 스키마 확인·보조 자료로 사용 가능하다.
- 운영 DB를 MVP 개발처럼 임의로 초기화하지 않는다.

## 검토한 대안

| 대안 | 고려한 장점 | 주요 부담·제약 | 판단 |
|---|---|---|---|
| Hibernate `ddl-auto=update/create` | 개발 초기 테이블 생성 편의성 | 예상치 못한 DDL·데이터 손상·환경 차이 위험 | **전 환경 미채택** |
| 수동 SQL + 스키마 덤프만 관리 | 개발 중 DDL 변경 자유도, 현재 구조 확인 용이 | 적용 순서·환경별 변경 이력·누락 관리가 어려움 | **MVP 실험 단계에 한정** |
| MVP 시작부터 Flyway 이력 누적 | 모든 변경 추적·환경별 재현 용이 | 잦은 스키마 실험에서 불필요한 마이그레이션 누적 | 초기 단계 미채택 |
| **MVP 완료 후 Flyway `V1` + 이후 버전별 SQL** | 개발 유연성 유지, 운영부터 이력과 재현성 확보 | 최종 스키마와 빈 DB 검증·전환 절차 필요 | **채택** |
| 운영 앱 기동 시 Flyway 자동 실행 | 누락된 마이그레이션 적용이 쉬움 | 재시작과 스키마 변경 결합, 런타임 DDL 권한 부담 | 운영 미채택 |
| **운영 배포 단계에서 Flyway 별도 실행** | 변경 시점·권한·실패 원인 통제 | 안전한 DB 접속 경로와 배포 절차 필요 | **채택** |

**백업·복구 대안**

| 대안 | 고려한 장점 | 주요 부담·제약 | 판단 |
|---|---|---|---|
| 정기 `pg_dump`만 사용 | 휴대 가능한 논리 백업·스키마 확인 | 별도 보관·암호화·복구 자동화, 시점 복구 한계 | 보조 수단 |
| **RDS 자동 백업·PITR + 필요 시 수동 Snapshot** | 관리형 복구 기능과 위험 변경 시 복구 지점 확보 | 복구 인스턴스 전환·비용·복구 리허설 필요 | **채택** |

## 선택 근거 및 트레이드오프

스키마 덤프는 현재 상태를 보여주지만 어떤 변경이 어느 환경에 적용되었는지는 자동 관리하지 않는다. Flyway는 이력·검증에 유리하지만 SQL 자체의 안전성이나 데이터 복구를 보장하지는 않는다.
