# BE-ADR-001 — 백엔드 아키텍처

- **상태:** 승인
- **결정:** 2026-10-29
- **범위:** 오늘의 수산 백엔드

## 핵심 결론

**단일 Spring Boot 애플리케이션을 가벼운 모듈형 모놀리스로 구성한다.** 기본 호출 구조는 `Controller → Service → Repository`이며, 도메인 간에는 명시적으로 공개한 API만 사용한다.

## 배경

MVP는 가격 조회·집계, Price Insight, 최근 이슈, 품목별 STOMP 채팅, 데이터 수집을 제공한다. 1인 개발과 낮은 AWS 운영비를 고려해 배포 단위와 운영 인프라를 최소화해야 한다.

## 결정

- 하나의 배포 가능한 Spring Boot 애플리케이션으로 운영한다.
- `fish`, `price`, `insight`, `issue`, `chat`, `auth`, `collection` 등 기능 중심 패키지로 분리한다. 이름·경계는 구현 시 조정할 수 있다.
- 각 모듈의 Repository·내부 Service를 다른 모듈이 직접 사용하지 않도록 한다. 외부 공개 계약은 필요한 인터페이스 또는 공개 서비스로 제공한다.
- 모듈 내부 Service 간 DI에는 불필요한 인터페이스를 만들지 않는다.
- 여러 내부 기능을 조정해야 할 때만 Facade/Application Service를 도입한다.
- `package-private`는 **동일한 Java 패키지**에만 적용된다. 하위 패키지를 포함한 경계는 별도 아키텍처 규칙·테스트 도입을 검토한다.
- 초기부터 MSA, Gradle 다중 모듈, Spring Modulith를 강제하지 않는다.

## 검토한 대안

| 대안 | 고려한 장점 | 주요 부담·제약 | 판단 |
|---|---|---|---|
| 단순 모놀리스 | 단일 배포·개발 속도·초기 설정 최소화 | 도메인 간 Repository/Service 직접 참조가 누적되기 쉬움 | 미채택 |
| **가벼운 모듈형 모놀리스** | 단일 프로세스를 유지하면서 기능별 공개 API와 내부 구현의 경계 구분 | 패키지 규칙과 의존성 방향을 지속적으로 관리해야 함 | **채택** |
| 마이크로서비스(MSA) | 독립 배포·서비스별 확장 및 장애 격리 가능성 | 네트워크 통신, 분산 트랜잭션, 관측·배포·인프라 관리 부담 | MVP 미채택 |

> 모듈형 모놀리스의 **인터페이스·Facade·멀티 Gradle 모듈은 별도 선택 사항**이다. 모든 내부 Service에 인터페이스를 만들거나 Facade 계층을 의무화하지 않는다.

## 선택 근거 및 트레이드오프

- **장점:** 단일 배포·디버깅·트랜잭션 구성이 단순하면서 기능 간 결합을 제한할 수 있다.
- **비용:** 모듈 경계가 컴파일 시점에 완전히 강제되지는 않는다. 필요 시 ArchUnit/Spring Modulith를 검토한다.

## 재검토 조건

모듈 간 무분별한 참조가 증가하거나 서로 다른 배포·확장 요구가 발생할 때.
