# BE-ADR-008 — AI 실행 아키텍처

- **상태:** 초안 검토 중
- **작성일:** 2026-11-05
- **관련 문서:** BE-ADR-007, PD-008, PD-010, PD-011, POC-005

## 핵심 결론

**MVP에서는 Spring Boot에서 외부 LLM API를 직접 호출하는 구조를 채택한다.** 별도 Python Worker나 관리형 AI 워크플로는 초기 도입하지 않는다.

AI 작업은 사용자 요청과 분리된 백그라운드 작업으로 실행하며, PostgreSQL을 통해 실행 상태와 결과를 관리한다.

AI 호출 기능은 공통 인터페이스로 추상화하되, PDF 분석과 Price Insight는 각각 독립적인 입력·출력 계약과 검증 정책을 가진다.

## 1. 배경

오늘의 수산은 비정형 자료 추출과 가격 변화 설명에 AI를 활용한다.

POC-005에서 Gemini 기반 PDF 직접 분석의 기술적 가능성을 확인했으나, 실제 운영을 위한 실행 구조는 별도로 결정해야 한다.

MVP에서는 낮은 운영 비용, 구현 단순성, 실패 복구 및 데이터 신뢰성을 우선한다.

또한 Price Insight는 하루 1회 분석 후 저장된 결과를 제공하므로 사용자 요청마다 AI를 실시간 호출할 필요가 없다.

## 2. AI 실행 구조

1. Spring Scheduler 및 Orchestrator가 AI 작업 실행을 요청한다.
2. PostgreSQL에서 실행 대상과 중복 여부를 확인한다.
3. 백그라운드 실행기가 작업을 처리한다.
4. 공통 AI 호출 인터페이스를 통해 외부 LLM API를 호출한다.
5. 결과를 작업 유형별 스키마와 검증 규칙으로 검사한다.
6. 검증 결과와 실행 이력을 PostgreSQL에 저장한다.
7. 검증된 결과만 후속 처리 또는 게시 대상으로 전달한다.

AI 호출은 웹 요청 처리 스레드와 분리하며, 동시 실행량을 제한한다.

장시간 AI 호출이나 장애가 가격 조회 및 채팅 등 사용자 기능의 가용성을 저하시키지 않도록 한다.

## 3. AI 작업별 책임

| 작업          | AI의 역할                            | 검증 책임                                           |
| ------------- | ------------------------------------ | --------------------------------------------------- |
| PDF 분석      | 문서의 사실·수치·시장 동향 추출      | 스키마, 수치, 단위, 페이지 및 출처 검증             |
| Price Insight | 가격 변화에 대한 근거 기반 설명 생성 | 사실·해석 구분, 근거 연결, 수치 및 게시 적합성 검증 |

AI는 데이터 원천이나 최종 검증 주체가 아니다.

대표 가격지수 계산과 데이터 무결성 검증은 결정적 Java/SQL 로직에서 수행한다.

MVP에서 복수 AI Agent 간 자율 협업 구조는 도입하지 않는다.

## 4. 모델 및 실행 관리

- AI 제공업체에 대한 직접 의존을 호출 어댑터 내부로 제한한다.
- 작업 유형별 모델과 프롬프트를 독립적으로 관리할 수 있도록 한다.
- 모델, 프롬프트 및 출력 스키마 버전을 실행 이력에 기록한다.
- 입력 데이터와 문서 버전을 추적하여 동일 작업의 재실행과 결과 비교를 지원한다.
- 타임아웃, 제한적 재시도, Backoff 및 호출량 제한을 적용한다.
- 실패하거나 검증되지 않은 결과는 정상 게시 결과를 덮어쓰지 않는다.
- API 키 등 민감한 인증 정보는 코드 및 실행 로그에 노출하지 않는다.
- 외부 AI로 전달하는 자료의 전송 허용 여부를 사전에 확인한다.

구체적인 동시 실행 수, 타임아웃, 재시도 횟수 및 작업별 스키마는 구현 Tech Spec에서 정의한다.

## 5. 검토한 대안

| 대안                                    | 장점                                            | 단점                                    | 판단          |
| --------------------------------------- | ----------------------------------------------- | --------------------------------------- | ------------- |
| Spring Boot 직접 호출 + 백그라운드 작업 | 단일 배포, Java 생태계 활용, 낮은 초기 비용     | 프로세스 자원 공유, 실행 관리 직접 구현 | **채택 제안** |
| 별도 Python Worker                      | Python AI 라이브러리 활용, 자원 격리, 독립 배포 | 통신·배포·작업 관리 복잡도 증가         | 초기 미채택   |
| 관리형 AI 워크플로                      | 관리형 실행 및 재시도 기능                      | 비용·서비스 의존성·운영 복잡도          | 초기 미채택   |

## 6. 결정의 영향

**기대 효과**

- 별도 실행 서비스 없이 AI 기능 구현
- 기존 Spring·PostgreSQL 구성 재사용
- AI 제공업체와 도메인 로직의 결합 완화
- 작업 유형별 독립적인 검증 및 실행 이력 관리

**감수하는 비용**

- AI 작업과 웹 서버의 프로세스 자원 공유
- 실행 상태·재시도·복구 로직 직접 구현
- 처리량 증가 시 Worker 분리 필요성 재검토

AI 처리량 증가, 장시간 CPU·메모리 점유, Python 전용 라이브러리 의존성 또는 웹 서비스 가용성 저하가 확인되면 별도 Worker 구조로의 전환을 검토한다.
