# FE-ADR-005. 클라이언트 상태 관리 전략

| 항목                      | 내용                                              |
| ------------------------- | ------------------------------------------------- |
| 프로젝트                  | 오늘의 수산                                       |
| 작성일                    | 2026-10-23                                        |
| 선정 전략                 | **React 기본 Hooks + Next.js URL 상태 관리**      |
| 외부 전역 상태 라이브러리 | **MVP에서는 미도입**                              |
| 관련 문서                 | FE-ADR-001 (프레임워크), FE-ADR-003 (데이터 캐싱) |

## 1. 핵심 결론

MVP의 UI 상태는 React 기본 Hooks로 관리하고, **공유·복원이 필요한 차트 기간은 URL Search Params**로 관리한다. 가격·차트·Insight 등 서버 상태는 FE-ADR-003에서 선정한 **TanStack Query + Fetch API**에 맡긴다. Zustand 등 별도 전역 상태 라이브러리는 필요성이 확인되면 도입한다.

**선정 근거**

1. **단순성:** 1인 개발 MVP에서는 기본 Hooks로 대부분의 UI 상태를 관리할 수 있다.
2. **UX:** 차트 기간을 URL에 저장하면 새로고침·링크 공유·탐색 시 선택 상태를 복원하기 쉽다.
3. **책임 분리:** 로컬 UI 상태·URL 상태·서버 상태를 분리하여 불필요한 의존성과 중복 관리를 줄인다.

## 2. MVP 적용 기준

| 상태 유형               | 관리 방법                       | 오늘의 수산 예시                            |
| ----------------------- | ------------------------------- | ------------------------------------------- |
| 컴포넌트 UI             | `useState`, 필요시 `useReducer` | 모달, 아코디언, 차트의 임시 날짜 선택       |
| 가까운 컴포넌트 간 공유 | Props 전달, 필요시 Context      | 여러 UI 영역의 공통 선택 상태               |
| URL로 복원할 상태       | Next.js 경로·Search Params      | 품목 경로, 차트 기간 `?period=monthly`      |
| 서버 상태               | **TanStack Query + Fetch API**  | 최신 가격, 시계열, Price Insight, 최근 이슈 |
| 실시간 통신             | WebSocket + 관련 React Hooks    | 채팅 연결·메시지 수신                       |
| 복잡한 앱 전역 상태     | MVP에서 별도 도구 미도입        | 필요 시 Zustand 재검토                      |

**URL 예시:** `/seafood/mackerel?period=monthly`. 차트의 일시적 날짜 선택은 기본적으로 URL에 넣지 않는다.

> 모바일에서 다른 앱으로 이동했다가 복귀할 때 항상 새로고침되는 것은 아니다. 다만 탭이 재로드되거나 공유 링크를 열더라도 선택 기간을 복원할 수 있다는 점에서 URL 상태가 유리하다. 잘못된 기간 값은 기본값으로 처리한다.

## 3. 대안 및 도입 판단

| 대안                  | 역할·장점                            | 한계                                         | MVP 판단    |
| --------------------- | ------------------------------------ | -------------------------------------------- | ----------- |
| **React Hooks + URL** | 별도 의존성 없이 화면·탐색 상태 관리 | 멀리 떨어진 컴포넌트 간 복잡한 공유에는 불편 | **선정**    |
| Context API           | 제한된 범위의 상태 공유              | 상태가 커지면 Provider·리렌더링 관리 필요    | 필요시 사용 |
| Zustand               | 전역 클라이언트 상태를 Store로 공유  | 별도 의존성·상태 설계 필요                   | 도입 유보   |
| Redux Toolkit 등      | 큰 규모의 상태 흐름·추적 체계        | 초기 설정 및 운영 복잡성                     | MVP 미도입  |

### Zustand — 역할과 도입 기준

| 항목           | 내용                                                                                                      |
| -------------- | --------------------------------------------------------------------------------------------------------- |
| 무엇인가?      | React 컴포넌트 밖의 **클라이언트 상태를 Store로 관리·공유**하는 경량 라이브러리                           |
| 서비스 적용 예 | 여러 화면이 공통으로 참조하는 UI 필터, 채팅 패널 표시 상태 등                                             |
| 도입 기준      | Props 전달이 여러 단계로 반복되거나, 멀리 떨어진 컴포넌트 사이 상태 동기화·변경 추적이 실제로 어려워질 때 |
| MVP 결정       | **미도입**. Hooks·Props·필요시 Context로 시작                                                             |

### TanStack Query — 역할과 도입 기준

| 항목           | 내용                                                                                     |
| -------------- | ---------------------------------------------------------------------------------------- |
| 무엇인가?      | 서버에서 조회하는 비동기 데이터의 **캐싱·신선도·재조회·오류 상태**를 관리하는 라이브러리 |
| 서비스 적용 예 | 가격, 기간별 차트, Price Insight, 최근 이슈 조회                                         |
| 도입 기준      | 여러 화면에서 API 결과를 재사용하고 갱신·실패·중복 조회를 일관되게 관리해야 할 때        |
| MVP 결정       | **도입**. 세부 캐싱·재시도 정책은 FE-ADR-003을 따름                                      |

**구분:** Zustand는 클라이언트 전역 상태, TanStack Query는 서버 상태가 주된 책임이다. 동일한 가격 응답을 두 도구에 중복 저장하지 않는다.

## 4. 기술 회의 Q&A

**Q. 1인 개발 MVP에도 전역 상태 라이브러리가 필요한가?**  
A. 기본 Hooks와 URL·Props로 해결할 수 있는 상태가 대부분이므로 처음부터 도입하지 않는다. 공유 복잡성이 실제로 발생하면 재검토한다.

**Q. 차트 기간을 React 내부 상태가 아닌 URL로 관리하는 이유는?**  
A. 새로고침·브라우저 재로드·링크 공유 후에도 선택한 기간을 복원할 수 있어 UX에 유리하다. 단, 브라우저가 백그라운드 복귀 때 항상 새로고침되는 것은 아니다.

**Q. TanStack Query가 있다면 Zustand도 필요한가?**  
A. 아니다. 두 도구의 관리 대상이 다르며, 서버 상태는 FE-ADR-003에 따라 TanStack Query로 관리한다.

## 5. 트레이드오프 및 재검토

기본 Hooks 중심 구조는 단순하지만, 화면 수와 상태 공유 범위가 증가하면 Props 전달과 상태 추적이 복잡해질 수 있다. 차트 기간을 URL에 기록하면 복원성은 좋아지지만, 기본값·잘못된 쿼리 값·탐색 기록 처리 규칙이 필요하다.

**재검토 조건:** 공통 UI 상태의 다중 화면 공유가 빈번해지거나, Hooks·Context만으로 구현 난이도가 명확히 상승할 때 Zustand 도입을 검토한다. 채팅의 재접속·메시지 동기화 정책은 별도 기술 결정에서 다룬다.

## 6. 최종 결정

**React 기본 Hooks를 MVP 클라이언트 UI 상태 관리의 기본으로 채택하고, 품목·차트 기간처럼 복원·공유할 상태는 Next.js URL로 관리한다.** 서버 상태는 TanStack Query를 사용하며, 별도 전역 상태 라이브러리 도입은 유보한다.
