# FE-ADR-002. 프론트엔드 렌더링 전략 선정

| 항목      | 내용                                          |
| --------- | --------------------------------------------- |
| 프로젝트  | 오늘의 수산                                   |
| 작성일    | 2026-10-23                                    |
| 선정 전략 | **SSG + CSR**                                 |
| 기술 환경 | Next.js 16.x + React 19.x · App Router        |
| 관련 문서 | FE-ADR-001 프론트엔드 프레임워크 및 버전 선정 |

## 1. 핵심 결론

오늘의 수산 MVP의 렌더링 전략으로 **SSG(Static Site Generation) + CSR(Client-Side Rendering)** 조합을 선정한다.

공개 페이지의 기본 정보와 SEO 콘텐츠는 빌드 시 정적 HTML로 생성하고, 최신 가격·Price Insight·최근 이슈는 백엔드 API에서 조회한다. 실시간 채팅과 가격 차트의 상호작용은 클라이언트에서 처리한다.

### 선정 근거

1. **SEO:** 품목별 고유한 정적 HTML을 제공하여 검색엔진이 주요 콘텐츠를 JavaScript 실행 없이 읽을 수 있도록 한다.
2. **운영 효율:** 가격 데이터 갱신을 프론트엔드 재빌드·재배포와 분리하고, 정적 호스팅으로 서버 운영 비용을 절감한다.
3. **확장성:** 초기 3종부터 점진적으로 품목을 확대하면서 기존 페이지의 가격 갱신은 API로 처리하고, 신규 품목만 배포 시 정적 페이지에 추가한다.

## 2. 기술 선정 배경 및 요구사항

오늘의 수산은 공공 데이터를 기반으로 수산물 가격 차트, Price Insight, 최근 이슈 및 실시간 채팅을 제공하는 모바일 웹 서비스이다.

백엔드에서 배치 작업으로 가격과 분석 데이터를 미리 확보하므로, 사용자가 접속할 때마다 서버에서 HTML을 새로 생성할 필요성이 낮다.

또한 전체 인프라 운영 예산을 월 30,000원 이내로 계획하고 있으며, 데이터 갱신에 일정한 지연을 허용한다.

| 요구사항       | 기술적 고려사항                            |
| -------------- | ------------------------------------------ |
| 검색엔진 유입  | 검색 가능한 초기 HTML과 품목별 고유 콘텐츠 |
| 모바일 사용성  | 빠른 초기 콘텐츠 전달 및 차트 상호작용     |
| 최신 가격 제공 | 백엔드 배치 완료 후 API 조회               |
| Price Insight  | 생성·저장된 분석 결과 조회                 |
| 실시간 채팅    | 클라이언트 기반 실시간 통신                |
| 운영 비용      | 월 30,000원 이내                           |
| 품목 확장      | 초기 3종에서 점진적 확대                   |
| 배포 효율      | 가격 갱신과 프론트엔드 배포 분리           |

### 2.1 렌더링 방식 및 관련 개념

| 구분              | 용어                                  | 개념                                                                            |
| ----------------- | ------------------------------------- | ------------------------------------------------------------------------------- |
| 애플리케이션 구조 | SPA (Single Page Application)         | 페이지 이동 시 전체 HTML을 다시 불러오지 않고 JavaScript로 화면을 전환하는 구조 |
| 렌더링 방식       | CSR (Client-Side Rendering)           | 브라우저에서 JavaScript를 실행하여 화면을 생성하는 방식                         |
| 렌더링 방식       | SSR (Server-Side Rendering)           | 사용자 요청 시 서버에서 HTML을 생성하여 전달하는 방식                           |
| 렌더링 방식       | SSG (Static Site Generation)          | 빌드 시 HTML을 미리 생성하여 사용자에게 제공하는 방식                           |
| 정적 페이지 갱신  | ISR (Incremental Static Regeneration) | 전체 재빌드 없이 기존 정적 페이지를 재생성하여 갱신하는 방식                    |

**개념 구분:** SPA는 페이지 이동 구조이며, CSR·SSR·SSG는 HTML 생성 시점을 결정하는 렌더링 방식이다. ISR은 정적 페이지를 갱신하기 위한 전략으로, 여러 방식을 조합하여 사용할 수 있다.

## 3. 렌더링 전략 비교

| 전략          | 장점                                                    | 단점 및 제약                                         | 판단     |
| ------------- | ------------------------------------------------------- | ---------------------------------------------------- | -------- |
| CSR 중심 SPA  | 구조 단순, 데이터 갱신 용이, 정적 호스팅 가능           | 주요 콘텐츠의 검색엔진 수집이 JavaScript 실행에 의존 | 제외     |
| **SSG + CSR** | **검색용 HTML 제공, 낮은 운영비, API 데이터 갱신 독립** | **동적 콘텐츠 SEO 제한, 신규 경로 추가 시 재빌드**   | **선정** |
| SSR + CSR     | 요청 시점 최신 HTML 제공, 동적 SEO 콘텐츠 대응          | 서버 런타임 필요, 요청 처리·장애·운영 비용 증가      | 제외     |
| ISR + CSR     | 전체 재빌드 없이 정적 HTML 갱신, SEO·최신성 균형        | 서버 런타임 및 캐시 관리 필요, Static Export 미지원  | 제외     |

### 3.1 CSR 중심 SPA를 선택하지 않은 이유

일반적인 CSR 중심 SPA는 가격 차트와 실시간 채팅 등 상호작용 구현에 적합하다.

그러나 오늘의 수산은 검색엔진을 통한 신규 사용자 유입이 중요하다. 주요 콘텐츠를 API 조회 후에만 렌더링하면 검색엔진의 JavaScript 처리에 대한 의존성이 커진다.

SSG를 통해 검색 가능한 초기 HTML을 제공하는 것이 더 적합하다고 판단하였다.

### 3.2 SSR을 선택하지 않은 이유

SSR은 요청 시점에 최신 가격과 Price Insight를 포함한 HTML을 생성할 수 있다.

다만 오늘의 수산은 백엔드에서 데이터를 사전 수집·저장하며, 초 단위 최신 HTML 생성을 요구하지 않는다.

따라서 동적 HTML의 이점보다 서버 운영 비용과 복잡성이 크다고 판단하였다.

### 3.3 ISR을 선택하지 않은 이유

ISR은 전체 사이트를 다시 빌드하지 않고도 정적 HTML을 갱신할 수 있어 SEO와 데이터 최신성 측면에서 유리하다.

하지만 Next.js Static Export에서는 ISR을 지원하지 않으며, 별도의 서버 실행 및 캐시 관리 환경이 필요하다.

초기 품목 수와 제한된 운영 예산을 고려해 MVP에서는 도입하지 않는다.

## 4. 선정 전략의 장점 및 트레이드오프

| 영역          | 기대 효과                                  | 트레이드오프                               |
| ------------- | ------------------------------------------ | ------------------------------------------ |
| SEO           | 품목별 정적 HTML과 메타데이터 제공         | 최신 가격·Insight의 검색 색인 불확실성     |
| 렌더링        | 정적 HTML을 CDN에서 전달                   | CSR 콘텐츠는 JavaScript·API 실행 이후 표시 |
| 데이터 최신성 | 배치 완료 후 API 조회로 최신 데이터 제공   | API 응답 지연·실패 처리 필요               |
| 배포          | 가격 갱신 시 프론트엔드 재배포 불필요      | 정적 콘텐츠 변경은 재빌드 필요             |
| 서버 비용     | 별도 Next.js 렌더링 서버 불필요            | 요청 시점 SSR·ISR 사용 불가                |
| 품목 확장     | 기존 페이지의 데이터 갱신 비용과 빌드 분리 | 신규 품목 URL 생성 시 재빌드 필요          |

### 4.1 SEO 트레이드오프

SSG로 생성한 HTML에는 품목명, 기본 설명, 가격 데이터의 의미, 집계 기준 및 SEO 메타데이터를 포함한다.

실제 가격 수치와 Price Insight는 CSR로 조회하므로 검색엔진의 JavaScript 렌더링 여부에 따라 일부 콘텐츠가 색인되지 않을 수 있다.

이는 SEO를 포기하는 것이 아니라 **최신 동적 콘텐츠의 검색 노출 가능성 일부를 감수하고 운영 단순성과 비용 효율성을 우선한 결정**이다.

또한 SSR로 전환하더라도 콘텐츠의 고유성·유용성이 부족하다면 검색 순위 향상을 보장할 수 없다.

### 4.2 품목 확장 트레이드오프

Static Export에서는 빌드 시 생성하지 않은 동적 경로를 요청 시점에 자동 생성할 수 없다.

따라서 신규 품목을 추가할 때는 정적 페이지 생성 및 재배포가 필요하다.

초기 품목은 3종이며 이후에도 데이터 확보와 검증을 거쳐 점진적으로 확대하므로, 현 단계에서는 해당 제약을 수용한다.

단, 전체 품목 수가 크게 증가하면 신규 품목 1종 추가 시에도 전체 정적 페이지 생성 비용이 발생할 수 있으므로 빌드 시간을 재평가해야 한다.

## 5. 오늘의 수산 적용 방식

| 화면·기능      | 렌더링    | 제공 콘텐츠                            |
| -------------- | --------- | -------------------------------------- |
| 홈             | SSG + CSR | 정적 화면 구성, 최신 가격은 API 조회   |
| 수산물 상세    | SSG + CSR | 품목별 고유 HTML, 최신 가격은 API 조회 |
| 가격 차트      | CSR       | 시계열 조회, 기간·날짜 선택            |
| Price Insight  | CSR       | 백엔드에 저장된 분석 결과 조회         |
| 최근 이슈      | CSR       | 최신 기사·공공자료 조회                |
| 실시간 채팅    | CSR       | WebSocket 메시지 송수신                |
| 고정 안내·정책 | SSG       | 변경이 적은 정적 콘텐츠                |

### 5.1 검색용 HTML 구성

품목별 정적 HTML에는 다음 정보를 제공한다.

- 고유 URL 및 페이지 제목
- 수산물 품목별 고유 설명
- 가격 데이터의 의미와 집계 기준
- 관측 기준 및 데이터 출처에 대한 설명
- SEO 메타데이터

모든 품목에 동일한 설명만 반복하지 않고, 실제 데이터 정책에 맞는 유용한 콘텐츠를 제공한다.

### 5.2 데이터 갱신 흐름

```text
백엔드 배치 작업
    ↓
가격·분석 데이터 검증 및 저장
    ↓
새 데이터 공개
    ↓
프론트엔드 API 조회
    ↓
최신 가격·Price Insight 화면 반영
```

배치가 진행 중이거나 실패한 경우 이전에 검증된 데이터를 유지할 수 있도록 백엔드에서 데이터 공개 시점을 관리한다.

프론트엔드에서는 관측 기준일과 데이터 갱신 시각을 구분하여 표시한다.

API 캐싱, 재조회 시점 및 데이터 무효화 정책은 FE-ADR-003에서 별도로 결정한다.

## 6. 기술 회의 주요 질문과 결정 근거

렌더링 전략을 선정하는 과정에서 검토한 질문과 답변을 기록한다.

### Q1. 백엔드에서 배치로 데이터를 확보한다면 프론트엔드 재빌드가 필요한가?

**답변:** 기존 품목의 가격이나 Insight가 변경되는 경우에는 재빌드가 필요하지 않다. 브라우저에서 API를 다시 조회하면 갱신된 데이터를 표시할 수 있다.

다만 정적 HTML 자체의 내용을 변경하려면 재빌드·재배포가 필요하다.

**결정:** 데이터 갱신과 프론트엔드 배포를 분리한다.

### Q2. 배치가 예정 시간보다 늦게 완료되면 문제가 발생하는가?

**답변:** 일정한 갱신 지연을 허용하므로 배치 완료 시점이 수초 또는 수분 변동되는 것은 수용할 수 있다.

중요한 것은 완료되지 않은 데이터를 노출하지 않는 것이며, 백엔드는 검증된 데이터만 공개해야 한다.

**결정:** 프론트엔드가 배치 완료 시각에 직접 의존하지 않도록 한다.

### Q3. 최신 가격과 Price Insight를 HTML에 포함하지 않으면 SEO에 불리한가?

**답변:** 검색엔진이 JavaScript를 실행하지 않거나 API 콘텐츠를 정상적으로 처리하지 못하면 해당 정보가 색인되지 않을 수 있다.

반면 주요 정보를 초기 HTML에 포함하면 검색엔진의 수집 안정성과 검색어 관련 콘텐츠의 가시성을 높일 수 있다. 그러나 검색 순위 상승 자체를 보장하지는 않는다.

**결정:** 동적 콘텐츠 SEO의 일부 기회를 감수하고, 정적 HTML의 고유성과 정보 품질을 강화한다.

### Q4. SSG에서 가격이 변경될 때마다 빌드하면 운영 비용이 커지지 않는가?

**답변:** 정적 HTML에 최신 가격을 포함하면 가격 갱신마다 재빌드가 필요할 수 있다.

금전적 비용뿐 아니라 배치·빌드·배포 실패를 함께 관리해야 하는 운영 복잡성이 발생한다.

**결정:** 정적 HTML에는 안정적인 콘텐츠를 제공하고, 가격 갱신은 API로 처리한다.

### Q5. 수산물 품목이 3종에서 100종, 1,000종으로 늘어나면 어떻게 되는가?

**답변:** 품목별 정적 페이지 수가 증가하므로 전체 빌드 시간과 빌드 시 데이터 조회 비용이 늘어날 수 있다.

다만 기존 품목의 가격 변경은 API로 처리하므로, 품목 증가가 곧바로 매일의 재배포 증가를 의미하지는 않는다.

**결정:** 초기에는 전체 품목을 SSG로 생성하고, 실제 품목 수와 빌드 비용이 증가하면 재검토한다.

### Q6. SEO 성과가 낮다면 SSR로 전환하면 되는가?

**답변:** SSR은 동적 콘텐츠를 초기 HTML에 포함하기 유리하지만 검색 성과를 보장하지 않는다.

검색 유입 부족의 원인이 콘텐츠 품질인지, 크롤링·색인 문제인지, 렌더링 방식인지 먼저 구분해야 한다.

**결정:** 검색 성과를 측정하고 렌더링 방식이 실제 원인으로 확인되는 경우에만 전환을 검토한다.

## 7. 재검토 조건

다음 상황에서는 렌더링 전략을 재검토한다.

| 조건                                                   | 재검토 방향                      |
| ------------------------------------------------------ | -------------------------------- |
| 최신 가격·Insight의 검색 색인이 필수 요구사항으로 변경 | ISR·SSR 검토                     |
| 검색 성과 분석에서 CSR 콘텐츠 수집 문제가 확인         | 서버 렌더링 범위 확대 검토       |
| 정적 페이지 증가로 빌드 시간이 운영에 부담             | ISR 또는 선택적 동적 렌더링 검토 |
| 신규 품목의 추가·공개 빈도가 크게 증가                 | 페이지 생성 및 배포 전략 검토    |
| 개인화된 서버 렌더링 필요성 발생                       | SSR 및 서버 런타임 도입 검토     |

## 8. 최종 결정

**Next.js 16 + React 19 기반의 SSG + CSR 렌더링 전략을 채택한다.**

검색엔진에는 품목별 고유한 정적 HTML을 제공하고, 최신 가격·Price Insight·최근 이슈는 백엔드 API를 통해 조회한다.

가격 데이터 갱신과 프론트엔드 배포를 분리하여 월 30,000원 이내의 운영 예산과 단순한 서비스 구조를 우선한다.

신규 품목 추가 시 재빌드가 필요한 제약과 동적 콘텐츠의 SEO 불확실성을 수용하며, 실제 운영 지표를 바탕으로 향후 렌더링 전략을 재검토한다.
