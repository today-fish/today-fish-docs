# FE-ADR-003. 데이터 캐싱 및 갱신 전략

| 항목      | 내용                                                            |
| --------- | --------------------------------------------------------------- |
| 프로젝트  | 오늘의 수산                                                     |
| 작성일    | 2026-10-23                                                      |
| 선정 기술 | **TanStack Query + Fetch API**                                  |
| 기본 정책 | **staleTime 30분 · gcTime 60분**                                |
| 관련 문서 | FE-ADR-001 프레임워크 및 버전 선정, FE-ADR-002 렌더링 전략 선정 |

## 1. 핵심 결론

오늘의 수산 MVP의 클라이언트 데이터 캐싱에는 **TanStack Query + Fetch API**를 사용한다.

가격 데이터를 기준으로 `staleTime` 30분, `gcTime` 60분을 적용하며, 브라우저 메모리에서 품목·조회 조건별로 캐시를 관리한다.

초기 MVP에서는 **캐싱의 단순성과 안정적인 오류 처리**를 우선하고, 배치 완료 연동 및 캐시 고도화는 실제 운영 지표를 확보한 뒤 진행한다.

### 핵심 선정 근거

1. **유지보수:** 데이터 캐싱·재조회·상태 관리를 TanStack Query에 맡겨 자체 구현을 줄인다.
2. **효율성:** 30분 신선도와 조건별 캐시를 활용해 불필요한 가격 API 요청을 줄인다.
3. **안정성:** 재조회 실패 시 기존 정상 데이터를 보존하고, 최초 조회 실패 시 해당 영역에만 오류를 표시한다.

## 2. 기술 선정 배경 및 요구사항

초기 제공 품목은 PRD-001에서 정의하며, 프론트엔드는 품목·조회 조건별 캐싱 정책을 적용한다.

| -------------- | -------------------------------------- |

## 3. 기술 대안 비교

| 기술                           | 장점                                                      | 단점 및 제약                                                | 판단     |
| ------------------------------ | --------------------------------------------------------- | ----------------------------------------------------------- | -------- |
| Fetch API + React 직접 구현    | 추가 의존성 없음, 동작 직접 제어                          | 캐싱·무효화·재조회·중복 요청 로직 직접 구현                 | 제외     |
| **TanStack Query + Fetch API** | **서버 상태 캐싱, Query Key, 재조회, 선택적 무효화 제공** | **추가 의존성 및 설정·정책 이해 필요**                      | **선정** |
| SWR + Fetch API                | 간결한 API, 캐시와 재검증 지원                            | 프로젝트의 상세 오류·무효화 정책에 대한 별도 구현·검토 필요 | 대안     |

### 3.1 Fetch API만 사용하지 않은 이유

Fetch API는 HTTP 요청을 수행하지만, 여러 화면에서 서버 응답을 캐싱하고 공유하는 기능까지 제공하지는 않는다.

오늘의 수산은 품목·기간별 캐시와 재조회 실패 시 이전 데이터 유지가 필요하므로 자체 상태 관리 코드를 늘리기보다 전용 라이브러리를 활용한다.

### 3.2 TanStack Query를 선택한 이유

TanStack Query는 서버 상태를 조회·캐싱하고, 신선도와 비활성 캐시 보존시간을 관리하며, Query Key에 따른 선택적 무효화를 지원한다.

다만 `Retry-After`, 점진적 실패 쿨다운 등 프로젝트별 정책은 기본 기능만으로 완성되지 않으므로 별도 설계가 필요하다.

MVP에서는 이러한 고급 제어 기능을 최소화한다.

## 4. MVP 적용 정책

| 항목             | 결정                                                        |
| ---------------- | ----------------------------------------------------------- |
| 서버 상태 관리   | TanStack Query                                              |
| HTTP 요청        | Fetch API                                                   |
| 가격 `staleTime` | **30분**                                                    |
| 기본 `gcTime`    | **60분**                                                    |
| 캐시 저장 범위   | 브라우저 메모리                                             |
| 재조회 시점      | 오래된 캐시로 페이지 재진입·탭 복귀 시                      |
| 주기적 폴링      | 사용하지 않음                                               |
| 캐시 키          | 품목·기간 등 조회 조건별 구분                               |
| 캐시 무효화      | 관련 Query Key에 한정                                       |
| 재조회 실패      | 기존 정상 데이터 유지 + 갱신 실패 안내                      |
| 최초 조회 실패   | 실패 영역에만 오류 표시                                     |
| 자동 재시도      | 재시도 가능한 일시적 오류에 최대 1회                        |
| 자동 재시도 지연 | 1~3초 무작위 지연(Jitter)                                   |
| 수동 재시도      | 중복 요청 차단, 최소 5초 클릭 간격, 요청당 자동 재시도 없음 |
| 서버 요청 제한   | `Retry-After`가 있으면 서버 지침 준수                       |

### 4.1 캐시 신선도와 보존시간

`staleTime`과 `gcTime`은 서로 다른 설정이다.

- `staleTime`: 마지막 성공 조회 이후 데이터를 신선하다고 간주하는 시간
- `gcTime`: 사용 중이지 않은 Query를 메모리에 보관하는 시간

30분이 지나도 데이터가 즉시 삭제되지는 않는다. 오래된 캐시로 화면에 다시 진입하면 기존 값을 표시하면서 API 재조회를 수행할 수 있다.

단, `gcTime` 만료로 해당 캐시가 이미 제거되었다면 신규 조회가 필요하다.

### 4.2 캐시 보존 범위

MVP에서는 메모리 캐시만 사용한다.

페이지 이동 중에는 Query Cache를 재사용할 수 있지만, 새로고침·탭 종료 후에는 캐시가 초기화될 수 있다.

브라우저 저장소 영속화와 탭 간 캐시 공유는 도입하지 않는다.

### 4.3 데이터별 캐시 키

캐시는 조회 결과를 구분할 수 있도록 데이터 유형·품목·기간 등의 조건을 포함한다.

예시:

- `['price', 'mackerel']`
- `['chart', 'mackerel', '15d']`
- `['chart', 'mackerel', 'monthly']`
- `['insight', 'mackerel', '15d']`
- `['issues', 'mackerel']`

특정 데이터가 변경되었다면 관련 캐시만 무효화한다.

단, 무효화된 활성 Query는 백그라운드 재조회가 발생할 수 있으므로, 대량 일괄 무효화는 피한다.

### 4.4 데이터 유형별 정책

MVP에서는 복잡한 신선도 정책을 데이터 유형별로 세분화하지 않는다.

가격 데이터의 30분 정책을 기본값으로 활용하되, 실제 데이터 수집 주기와 API 호출량을 확인한 후 가격 차트·Price Insight·최근 이슈의 별도 캐싱 정책이 필요한지 검토한다.

가격과 Price Insight의 데이터 버전 일관성은 백엔드 데이터 공개 정책과 함께 검토해야 하며, 단순히 같은 `staleTime`을 적용하는 것만으로 정합성이 보장되지는 않는다.

## 5. 오류 및 재시도 정책

### 5.1 이전 데이터가 있는 경우

API 재조회에 실패하면 기존 정상 캐시를 삭제하지 않는다.

사용자에게 이전 가격을 표시하면서 최신 정보를 확인하지 못했음을 알린다.

가격의 실제 관측일과 마지막 API 조회 성공 시각은 구분한다.

### 5.2 이전 데이터가 없는 경우

최초 조회에 실패하면 해당 데이터 영역에 오류 안내와 다시 시도 기능을 제공한다.

품목 설명 등 정상적인 정적 콘텐츠까지 전체 오류 화면으로 전환하지 않는다.

### 5.3 자동 재시도

MVP에서는 네트워크 오류와 HTTP 408·429·500·502·503·504를 일시적 오류 후보로 구분하며, 최초 요청 외 자동 재시도는 최대 1회로 제한한다.

재시도 간격은 1~3초 Jitter를 기본으로 한다.

유효한 `Retry-After`가 존재하면 서버 지침을 우선한다. 자동 재시도 허용 대기시간이 10초를 넘는 경우 자동 재시도를 포기하되, 서버가 지정한 요청 제한을 앞당겨 해제하지 않는다.

### 5.4 수동 재시도

수동 재시도는 사용자가 직접 요청할 수 있도록 제공하되 다음을 적용한다.

- 동일 요청이 진행 중이면 중복 요청하지 않는다.
- 클릭 간격은 최소 5초로 제한한다.
- 수동 요청에 추가 자동 재시도를 붙이지 않는다.
- 서버의 `Retry-After` 제한을 준수한다.
- 성공 시 정상 캐시로 갱신하고, 실패 시 이전 데이터 및 오류 안내를 유지한다.

## 6. 기술 회의 주요 질문과 결정 근거

### Q1. 백엔드 배치가 끝나면 프론트엔드 캐시를 즉시 무효화해야 하는가?

**답변:** 배치 완료 이벤트를 통해 갱신할 수 있으나, 초기 정적 배포 환경에는 상시 실행되는 Next.js 서버가 없다.

**결정:** MVP에서는 주기적 폴링이나 배치 완료 이벤트 연동 대신, 재진입·탭 복귀에 따른 조건부 재조회를 사용한다.

### Q2. 재조회에 실패하면 이전 가격을 삭제해야 하는가?

**답변:** 일시적인 API 장애로 정상 관측 데이터를 제거하면 서비스 사용성이 떨어진다.

**결정:** 이전 데이터를 유지하고, 최신 정보 확인 실패를 명시한다.

### Q3. 가격이 오래됐는지는 프론트엔드에서 계산해야 하는가?

**답변:** 시장 휴장일, 정상 갱신 기대일, 품목별 결측 등 원천 데이터 특성을 고려해야 하므로 백엔드에서 판단하는 것이 적절하다.

**결정:** 백엔드는 데이터 품질을 판정하고 프론트엔드는 이를 표현한다. 품질 판정 기준은 실제 데이터 검증이 필요하다.

### Q4. 캐시 무효화 시 요청이 한꺼번에 몰리지 않는가?

**답변:** 다수의 클라이언트가 동시에 갱신하면 요청 집중이 발생할 수 있다. Jitter, 공통 응답 캐시, 요청 통합 등의 대응 방법이 존재한다.

**결정:** MVP에서는 일괄 무효화를 피하고 요청 재시도 횟수를 제한한다. 본격적인 스탬피드 대응은 부하 측정 후 검토한다.

### Q5. 복잡한 실패 쿨다운 정책까지 MVP에서 구현해야 하는가?

**답변:** 연속 실패 시 1분·2분·최대 5분의 점진적 쿨다운은 반복 요청을 억제하는 데 유용하지만, 별도 상태 관리가 필요하다.

**결정:** 기술적 방향은 검토했으나 MVP 구현에서는 제외하고 후속 고도화 과제로 이관한다.

### Q6. 새로고침 후에도 캐시를 유지해야 하는가?

**답변:** 브라우저 저장소 영속화는 가능하지만 복원·만료·스키마 관리가 추가된다.

**결정:** MVP에서는 메모리 캐시만 사용한다.

### 재검토 조건

다음 중 하나가 확인되면 캐싱 정책을 재검토한다.

- API 요청량 또는 응답시간이 목표 수준을 벗어나는 경우
- 배치 완료 이후 데이터 반영 지연이 실제 사용자 문제로 확인되는 경우
- 반복 재조회로 백엔드 부하가 증가하는 경우
- 가격과 Price Insight의 기준 데이터 불일치가 발생하는 경우
- 차트 캐시 크기로 브라우저 메모리 사용량이 과도해지는 경우

## 9. 최종 결정

**오늘의 수산 MVP에는 TanStack Query + Fetch API를 사용한다.**

가격 데이터는 `staleTime` 30분, `gcTime` 60분으로 설정하고, 품목·조회 조건별 메모리 캐시를 사용한다.

API 재조회 실패 시 기존 데이터를 유지하고, 최초 조회 실패 시 해당 영역에만 오류를 표시한다.

배치 완료 이벤트 연계, 점진적 쿨다운, 캐시 스탬피드 대응 및 데이터별 정밀한 신선도 관리는 실제 운영 지표를 확보한 뒤 단계적으로 도입한다.
