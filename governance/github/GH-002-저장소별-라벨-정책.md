# GH-002 — 저장소별 라벨 정책

- **버전:** V1
- **상태:** 승인
- **적용 범위:** today-fish Docs·Backend·Frontend Repository Labels
- **실제 값 확인일:** 2026-11-13
- **관련 문서:** [GH-001 이슈 분류 및 필드 정책](GH-001-이슈-분류-및-필드-정책.md), [GH-003 작업 계층 및 분할 기준](GH-003-작업-계층-및-분할-기준.md), [Docs 기여 규칙](../../.github/CONTRIBUTING.md)

## 핵심 결론

라벨은 **Repository 안에서 변경의 목적이나 기술 범위를 빠르게 찾기 위한 표시**다. Docs PR에는 `type: *`와 `area: *`, Backend·Frontend 작업에는 `scope: *`를 사용한다. 최초 구현 완료 후의 Backend·Frontend 작업에는 `Maintenance`를 더한다. 이 문서는 세 Repository의 실제 라벨 이름·색상·설명을 찾는 단일 목록이다.

## 1. 어떤 라벨을 선택하나요?

1. **Docs PR:** 변경 목적에 맞는 `type: *` 하나와 실제로 바꾼 영역의 `area: *` 하나 이상을 고른다. 예를 들어 문서 탐색 규칙을 정리한 PR은 `type: Docs`와 `area: Docs`다.
2. **Backend 작업:** 주된 기술 범위의 `scope: *`를 고른다. 가격 조회 Controller·DTO가 중심이면 `scope: API`, 가격 집계 규칙이 중심이면 `scope: Logic`이다.
3. **Frontend 작업:** 화면 자체라면 `scope: Screen`, 백엔드 응답 연동이 중심이면 `scope: APIIntegration`처럼 실제 변경 목적을 고른다.
4. **완료 후 유지보수:** Backend·Frontend에서 최초 구현 후 생긴 Bug·개선·리팩터링에는 `Maintenance`를 붙이고 필요한 Scope도 함께 고른다. Docs에는 이 라벨이 없다.

복수 Area·Scope는 서로 다른 영역을 실제로 변경하고 각각 검토해야 할 때 사용한다. 예를 들어 API와 DB 스키마를 함께 변경한다면 Backend의 `scope: API`·`scope: DB`를 함께 검토할 수 있다. 단순히 README 링크만 고친 경우에는 별도 Area를 늘리지 않는다.

Organization Issue Type `Feature`는 **Issue의 일 종류**다. Docs PR Label `type: Feature`는 **PR의 변경 목적**이다. 이름이 같아도 서로 자동으로 따라가지 않는다. Issue Type과 Project 필드는 [GH-001 필드 선택 가이드](GH-001-이슈-분류-및-필드-정책.md)를 참고한다.

## 2. 실제 라벨 이름과 확인 방법

- Prefix는 소문자이며 콜론 뒤에 공백을 정확히 하나 둔다.
- 값은 PascalCase로 쓰고 복합 이름에 공백·하이픈·슬래시를 넣지 않는다. `API`, `DB`, `UX`, `SEO` 같은 약어는 대문자를 유지한다.
- `Maintenance`는 접두어가 없는 기존 예외다.
- 색상과 Description은 GitHub의 실제 값을 그대로 기록한다. 다음 목록은 2026-11-13 읽기 전용 조회 결과다. 라벨을 검색하거나 입력할 때 공백·대소문자를 포함한 **Label Name 전체**를 사용한다.

```bash
for repo in today-fish-docs today-fish-backend todat-fish-frontend; do
  gh label list --repo "today-fish/$repo" --json name,color,description --limit 100
done
```

## 4. Backend 작업에는 어떤 Scope를 붙이나요? (8개)

Backend Repository는 `today-fish/today-fish-backend`다. `scope: *`는 세부 기술 범위이며 Project의 `workstream=BE`와 다른 정보다.

| Label Name | HEX Color | Description |
|---|---|---|
| `scope: API` | `#1D76DB` | Contorller, DTO, API 및 검증 |
| `scope: DB` | `#0E8A16` | 스키마, Flyway, 쿼리, 데이터베이스 작업 |
| `scope: Integration` | `#006B75` | 외부 API, 데이터 수집 연동 |
| `scope: LoadTest` | `#D97706` | 부하 테스트, 처리량·병목 검증 |
| `scope: Logging` | `#64748B` | 로그, 모니터링 및 장애 진단 |
| `scope: Logic` | `#5319E7` | 도메인 규칙, 서비스 로직 구현, 개선 |
| `scope: Test` | `#BFDADC` | 단위·통합 테스트 및 테스트 환경 |
| `Maintenance` | `#cbe64b` | 최초 구현 완료 이후의 버그·개선·리팩터링 |

예를 들어 기존 가격 조회 API의 응답 오류를 고치는 경우 `scope: API`와 `Maintenance`를 적용한다. 완료된 L1에는 새 Sub-issue로 넣지 않고 관련 링크로 연결한다. 판단 기준은 [GH-003 유지보수 작업 가이드](GH-003-작업-계층-및-분할-기준.md)를 따른다.

`scope: API`의 Description에 있는 `Contorller`는 실제 등록값이다. 이 문서에서 임의로 고치거나 GitHub 설정을 바꾸지 않는다.

## 5. Frontend 작업에는 어떤 Scope를 붙이나요? (8개)

Frontend Repository의 실제 이름은 `today-fish/todat-fish-frontend`다. 철자를 임의로 `today`로 고쳐 링크를 만들지 않는다.

| Label Name | HEX Color | Description |
|---|---|---|

| `scope: UIUX` | `#D93F9C` | 컴포넌트·인터랙션·사용성 개선 |
| `scope: Accessibility` | `#D97706` | 키보드 접근성, 스크린리더, 웹 접근성 |

| `scope: Cache` | `#5319E7` | 클라이언트 캐싱, 재검증, 상태 관리 |

## 6. 잘못 붙였거나 새 라벨이 필요할 때

| 실수 | 확인할 것 |
|---|---|
| Docs Issue Type이 `Feature`이므로 PR도 `type: Feature`로 지정 | PR 자체의 주된 변경 목적을 다시 판단 |
| Backend Issue에 `scope: API`만 붙이면 Project Backend View에 표시될 것으로 기대 | Project 등록과 `Level=L2`·`workstream=BE` 확인 |
| 완료된 L1의 후속 Bug인데 `Maintenance`가 없음 | Backend·Frontend에서는 기존 라벨을 추가 |
| Docs 유지보수에 `Maintenance`를 검색 | Docs에는 해당 라벨이 없으므로 기존 Type/Area 사용 |

Project의 실제 `Maintenance` View 필터는 `is:issue label:Maintenance`로 확인됐다. View 사용과 문제 해결은 [GH-005 Project 사용 가이드](GH-005-프로젝트-뷰-및-자동화-정책.md)에 있다. 이 필터 때문에 Docs 유지보수 Issue는 현재 View에 표시되지 않는다.

새 라벨을 만들기 전에 다음 순서로 판단한다.

1. 새 라벨이 필요한지 판단할 때 먼저 Type·Level·Workstream·Status·Priority 또는 기존 Scope로 표현할 수 있는지 확인한다. 같은 정보를 나타내는 라벨을 추가하지 않는다.
2. 이름·색상·설명 변경이나 삭제 전에 세 Repository의 사용 중인 Issue·PR과 Project 필터·View·자동화의 정확한 라벨 문자열 참조를 확인한다. 영향과 이전 방법을 제시한 뒤 사용자 승인을 받는다.
3. 라벨을 변경한 후 이 문서의 실제 목록과 GitHub 값을 다시 조회해 대조한다. `Maintenance`나 기존 라벨을 사용 이력 확인 없이 삭제하지 않는다.
4. Project View의 필터는 확인했지만 라벨 변경 후 자동화 동작까지 검증한 것은 아니다. 변경 영향은 실제 설정과 사용 이력을 다시 확인한다.

현재 [CONTRIBUTING](../../.github/CONTRIBUTING.md)은 Docs PR의 Type·Area 라벨 적용 절차를 정의하며 실제 라벨 이름과 일치한다. 라벨 이름·HEX 색상·설명의 기준 목록은 이 문서에서 관리한다.
