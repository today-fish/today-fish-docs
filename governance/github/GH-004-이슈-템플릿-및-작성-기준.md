# GH-004 — 이슈 템플릿 및 작성 기준

- **버전:** V1
- **상태:** 승인
- **적용 범위:** today-fish Docs·Backend·Frontend Repository의 Issue 작성
- **관련 문서:** [GH-001 필드 정책](GH-001-이슈-분류-및-필드-정책.md), [GH-002 라벨 정책](GH-002-저장소별-라벨-정책.md), [GH-003 작업 분할 기준](GH-003-작업-계층-및-분할-기준.md), [GH-005 Project 사용 가이드](GH-005-프로젝트-뷰-및-자동화-정책.md)

## 핵심 요약

Issue를 만들기 전에 중복 작업을 찾고, **일의 종류(Type)**, **상위 목표인지 실행 작업인지(Level)**, **변경할 Repository**를 정한다. 본문에는 작업 범위와 완료 조건, 검증 방법을 적는다. 이 문서는 복사해 쓸 수 있는 **본문 예시**이며 실제 `.github/ISSUE_TEMPLATE/` 설정 파일은 아니다.

## 1. 어떤 Issue를 어디에 만드나요?

1. 세 Repository와 통합 Project에서 같은 목표·오류를 다루는 열린 Issue를 찾는다. 이미 다루는 작업이면 새 Issue 대신 기존 Issue에 범위·증거를 보탠다.
2. 사용자 기능이면 `Feature`, 실행 작업이면 `Task`, 기대 결과와 실제 결과가 다른 결함이면 `Bug`를 선택한다. 이는 Organization Issue Type이며 Docs PR의 `type: *` 라벨과 다르다.
3. 기능 전체나 독립 기술 목표의 범위·인수 조건을 관리하면 `L1`, 구현·검증 가능한 실행 단위면 `L2`를 선택한다. 단순 작업을 형식 때문에 L1로 감싸지 않는다. 상세 판단은 [GH-003](GH-003-작업-계층-및-분할-기준.md)을 따른다.
4. L1은 Docs Repository에 둔다. L2는 실제 변경 대상인 Backend·Frontend·Docs Repository에 둔다. 백엔드 인프라는 Backend, 프론트엔드 인프라는 Frontend, 공통 운영 정책 문서는 Docs에 둔다.
5. 기준 PRD·PF·UX·ADR·Tech Spec의 해당 절을 확인한 뒤 완료 조건을 쓴다. 선행 Issue가 있으면 링크와 착수 조건을 남긴다.

| 상황 | Type·Level | Issue를 둘 곳 |
|---|---|---|
| 가격 차트 기능 전체 | `Feature`·`L1` | Docs |
| 독립적인 백엔드 실행 환경 목표 | `Task`·`L1` | Docs |
| 가격 조회 API 구현 | `Task`·`L2` | Backend |
| 최초 구현 후 API 응답 오류 | `Bug`·`L2` 가능 | Backend; 완료된 L1에는 링크로 연결 |

예시는 실제 Issue가 아니다. Type의 의미는 [GH-001 필드 선택 가이드](GH-001-이슈-분류-및-필드-정책.md), L1/L2의 크기는 [GH-003 작업 분할 가이드](GH-003-작업-계층-및-분할-기준.md)를 따른다. Issue를 만든 뒤 실제 Label은 [GH-002 라벨 선택 가이드](GH-002-저장소별-라벨-정책.md)에서 고른다. `Priority` 옵션은 GitHub 실제 등록값을 아직 검증하지 못했다.

## 2. 예시 본문을 복사하기 전

아래 코드 블록은 **가상의 가격 차트 작업**이다. 각 예시의 `[해당 절 링크]`, `[Docs Issue 링크]`, `[관측 결과]` 같은 대괄호 항목을 실제 정보로 교체한다. 특히 관련 문서는 파일 목록만 적지 말고 결정에 필요한 절의 링크를 남긴다. 해당 사항이 없는 선택 항목은 `없음`으로 쓰거나 삭제한다.

| 양식 | 반드시 채울 것 | 상황에 따라 채울 것 |
|---|---|---|
| L1 Feature | 목표·사용자 가치, 포함 범위, 기준 문서, 상위 완료 조건 | 제외 범위, 하위 작업 계획·의존관계 |
| L1 기술 목표 | 목표, 적용 범위, 기준 문서, 검증 가능한 완료 조건 | 제외 범위, 필요한 L2 계획 |
| L2 Task | 구현 범위, 기준 문서, 완료·검증 조건, 최초 개발이면 Parent L1 링크 | 선행 작업; 완료된 L1의 Maintenance라면 Parent 대신 관련 링크 |
| Bug | 기대·실제 결과, 재현 절차, 영향, 검증 기준 | 원본 L1·PR 링크, 환경 차이 |

완료 조건은 “API 구현” 같은 작업 이름을 반복하지 말고 **어떤 결과를 확인하면 끝나는지** 적는다. 예를 들어 “승인된 기간·품목 요청의 응답과 데이터 없음 처리가 기준 문서와 일치한다”처럼 검증할 수 있게 쓴다.

## 3. 가격 차트 L1 Feature 본문

가격 차트처럼 BE와 FE가 함께 필요한 사용자 기능은 Docs에 `Feature`·`L1`로 등록한다. 두 영역을 함께 포함하는 L1이라면 `workstream`을 비워둘 수 있다. Docs에 있다는 이유만으로 `DOCS`를 지정하지 않는다.

다음은 **가상 작성 예시**다. 실제 Issue 번호나 현재 구현 상태를 뜻하지 않는다. 링크 대상은 등록 전에 실제 문서·절로 교체한다.

```markdown
## 목표와 사용자 가치
사용자가 품목별 가격 흐름을 차트에서 확인한다.

## 포함 범위
- 승인된 가격 조회 계약에 따른 데이터 제공
- 기간 선택과 차트 표시

## 제외 범위
- 이번 기능의 승인 문서에 없는 새 가격 산식

## 기준 문서
- PRD-001의 가격 차트 요구사항: [해당 절 링크]
- 관련 PF·UX·Tech Spec: [해당 절 링크]

## 완료 조건
- 승인된 기간·품목 선택 흐름이 동작한다.
- 데이터 없음·조회 실패 상태가 기준 UX와 일치한다.
- 필수 L2의 검증 근거를 확인한다.

## 하위 작업 계획
- Backend: 가격 조회 API 구현
- Frontend: 가격 차트 및 기간 선택 구현
- 선행 관계: API 응답 계약 확인 후 FE 연동 검증
```

## 4. 공통 백엔드 인프라 L1 본문

독립적으로 완료를 판단해야 하는 기술 목표도 L1이 될 수 있다. 이때 Type은 `Task`다. 변경 대상이 Backend여도 상위 목표 Issue는 Docs에 두며, `workstream`은 실제 목표가 BE에 한정되면 `BE`, 여러 영역이면 비워둘 수 있다.

```markdown
## 기술 목표
승인된 백엔드 실행·배포 기준을 한 번에 검증할 수 있다.

## 적용·제외 범위
- 적용: 백엔드 실행 환경과 검증 절차
- 제외: 승인되지 않은 새 인프라 기술 도입

## 기준 문서
- 관련 BE-ADR·환경 문서: [해당 절 링크]

## 완료 조건
- 필요한 L2 결과와 실행 증빙이 모인다.
- 상위 기술 목표의 검증 기준을 충족한다.

## 필요한 L2
- 실행 환경 구성
- 배포 경로 검증
```

## 5. 가격 조회 API L2 Task 본문

L2는 변경할 Repository에 `Task`·`L2`로 등록한다. 가격 조회 API라면 Backend, `workstream`은 `BE`다. 기본적으로 L2 하나를 PR 하나로 검증할 수 있게 작성한다. 실제 Scope Label은 [GH-002](GH-002-저장소별-라벨-정책.md)의 `scope: API` 등에서 변경 목적에 맞게 선택한다.

```markdown
## Parent L1
- 가격 차트 L1: [Docs Issue 링크]

## 구현 범위
- 승인된 가격 조회 계약에 맞는 API 응답 제공
- 입력 검증 및 데이터 없음·오류 처리

## 기준 문서
- 관련 PRD·PF·BE Tech Spec: [해당 절 링크]

## 완료 조건
- 요청·응답과 실패 동작이 기준 문서와 일치한다.
- 관련 PR에 검증 결과와 이 Issue 링크가 있다.

## 검증 방법
- 정상 기간·품목 조회
- 잘못된 입력과 데이터 없음 처리

## 선행 작업
- 없으면 없음, 있으면 Issue 링크와 필요한 결과
```

GitHub의 서로 다른 Repository 간 Parent/Sub-issue 연결 가능 여부는 아직 확인하지 못했다(`NOT VERIFIED`). 연결 기능을 사용할 수 없다면 L2 본문에 Docs L1 링크를 남기고, L1에도 관련 L2 링크를 기록한다. 완료된 L1의 후속 유지보수 Issue는 연결 기능이 가능해도 새 Sub-issue로 추가하지 않는다.

## 6. API 응답 오류 Bug 본문

버그는 재현 정보가 핵심이다. 최초 개발의 미완료 범위에서 발견했는지, 완료 후 새로 발견했는지 먼저 확인한다. 완료된 기능의 새 결함은 신규 Issue로 만들고 Backend·Frontend에서는 `Maintenance`를 붙인다. 완료된 L1의 새 Sub-issue로 추가하지 않는다.

```markdown
## 기대 결과
승인된 가격 조회 계약의 응답을 반환한다.

## 실제 결과
[관측한 응답과 발생 조건을 정확히 기록]

## 재현 절차
1. [환경·품목·기간]
2. [요청 또는 화면 조작]
3. [관측 결과]

## 영향 범위
- [영향 받는 기능·환경]

## 기준 문서·관련 Issue
- [계약 절 링크]
- [원본 L1 또는 관련 Issue 링크]

## 완료·검증 기준
- 같은 절차에서 기대 결과를 확인한다.
- 관련 회귀 검증 결과를 PR에 남긴다.
```

개인정보나 비밀값이 포함된 원본 응답을 Issue에 붙이지 않는다. 재현에 필요한 값만 안전하게 요약한다. `Bug`와 `Maintenance`는 각각 Type과 Label이므로 함께 사용할 수 있다. Docs에는 `Maintenance` 라벨이 없고, Docs 유지보수 PR에는 기존 Type/Area 라벨 규칙을 적용한다.

## 7. Issue 작성 후 무엇을 확인하나요?

| 확인할 것 | 적용 기준 |
|---|---|
| Type·Level | 일의 종류와 계층을 따로 선택한다. L1 기술 목표는 `Task`도 가능하다. |
| Repository·`workstream` | 저장 위치와 담당 영역을 따로 판단한다. `INFRA`는 별도 저장소 이름이 아니다. |
| Status | 생성 후 Project에서 실제 단계와 일치하는지 확인한다. Issue Open/Closed와 다르다. |
| Priority·날짜 | 필요한 경우 GH-001의 기준으로 입력하고 실제 UI 옵션을 확인한다. |
| Labels | 정확한 이름은 GH-002에서 찾는다. Issue Type을 라벨로 다시 만들지 않는다. |
| L1 연결 | Parent 관계가 가능하면 사용하고, 검증 전에는 본문 링크도 남긴다. |

Issue 본문과 필드를 저장한 뒤 실제 표시 결과를 다시 읽는다. 대괄호 예시 문구가 남아 있지 않은지, 문서 링크가 해당 절을 여는지, L1·L2 관계가 추적되는지 확인한다. Issue가 Project에서 보이지 않는다면 등록 여부와 `Level`·`workstream`·Label을 [GH-005 Project 사용 가이드](GH-005-프로젝트-뷰-및-자동화-정책.md)의 순서로 확인한다.
