# GH-001 — 이슈 분류 및 필드 정책

- **버전:** V1
- **상태:** 승인
- **적용 범위:** today-fish Organization과 통합 GitHub Project의 Issue 분류
- **관련 문서:** [GH-002 저장소별 라벨 정책](GH-002-저장소별-라벨-정책.md), [GH-003 작업 계층 및 분할 기준](GH-003-작업-계층-및-분할-기준.md), [Docs 기여 규칙](../../.github/CONTRIBUTING.md)

## 핵심 결론

Issue를 등록할 때는 먼저 **무슨 일인가(Type)**, **상위 목표인가 실행 작업인가(Level)**, **어느 영역의 일인가(Workstream)**를 정한다. 그런 다음 진행 단계(Status)와 처리 순서(Priority)를 기록한다. Repository는 Issue를 저장할 위치다. 같은 뜻을 여러 필드나 라벨에 중복 기록하지 않는다.

가격 차트 전체라면 Docs Repository의 `Feature`·`L1` Issue로 관리한다. 가격 조회 API 구현은 Backend Repository의 `Task`·`L2`·`BE` Issue다. 실제 본문 작성은 [GH-004 Issue 작성 가이드](GH-004-이슈-템플릿-및-작성-기준.md)를 따른다.

## 1. 어떤 필드를 어디에서 설정하나요?

2026-11-13 읽기 전용 조회에서 Organization Issue Type과 Project 필드의 이름·연결 관계를 확인했다. **VERIFIED**는 실제 조회 결과, **POLICY**는 합의된 사용 기준, **NOT VERIFIED**는 아직 확인하지 못한 설정이다. 화면의 실제 필드명 `workstream`·`우선순위`를 개념명과 구분해 사용한다.

| 개념 | 정책상 관리 위치 | 값 또는 형식 | 실제 확인 범위 |
|---|---|---|---|
| Type | Organization Issue Type | `Feature`, `Task`, `Bug` | VERIFIED: 세 Type의 이름·설명 |
| Level | Project `Level` | `L1`, `L2` | VERIFIED: 필드와 옵션 |
| Workstream | Project `workstream` | `BE`, `FE`, `DOCS`, `INFRA` | VERIFIED: 필드와 옵션 |
| Status | Project `Status` | `Backlog`, `Todo`, `In Progress`, `In Review`, `Done` | VERIFIED: 필드와 옵션 |
| Priority | Organization Issue Field → Project `우선순위` | `Urgent`, `High`, `Medium`, `Low` | VERIFIED: Issue Field 연결; 옵션은 POLICY이며 실제 등록 여부 NOT VERIFIED |
| Start date | Organization Issue Field → Project `Start date` | 날짜 | VERIFIED: Issue Field 연결; 입력 동작 NOT VERIFIED |
| Target date | Organization Issue Field → Project `Target date` | 날짜 | VERIFIED: Issue Field 연결; 입력 동작 NOT VERIFIED |

Project에는 `Effort`도 Issue Field로 연결되어 있다. 옵션과 운영 의미는 아직 정하지 않았으므로 임의로 사용 기준을 만들지 않는다. 실제 Label 이름·색상·설명은 [GH-002 라벨 선택 가이드](GH-002-저장소별-라벨-정책.md)에서 찾는다.

## 2. 어떤 Issue Type과 Level을 선택하나요?

Type은 **일의 종류**, Level은 **작업의 크기와 계층**이다. 둘은 별개로 선택한다.

| 값 | 선택 기준 |
|---|---|
| `Feature` | 사용자 기능의 범위와 완료 조건을 관리한다. |
| `Task` | 구현·개선·검증·인프라처럼 실행 가능한 작업을 관리한다. |
| `Bug` | 기대 동작과 실제 동작의 차이를 재현·수정한다. |

Docs PR의 `type: Feature` 라벨은 **PR의 변경 목적**을 표시한다. Organization Issue Type `Feature`와 이름이 비슷해도 같은 설정이 아니다.

| 값 | 의미 |
|---|---|
| `L1` | 기능 또는 독립 기술 목표의 범위·완료 조건을 관리하는 상위 Issue |
| `L2` | 구현·검증 가능한 실행 Issue; 유지보수 시에는 완료된 L1의 하위가 아닐 수 있음 |

예를 들어 가격 차트 전체는 `Feature`·`L1`, 가격 조회 API는 `Task`·`L2`, 최초 개발 완료 후 발견한 API 오류는 `Bug`·`L2`로 분류할 수 있다. 독립 기술 목표는 `Task`·`L1`도 가능하다. 완료된 L1과 유지보수 Issue의 연결 예외, 작업 크기 판단은 [GH-003 L1/L2 분할 가이드](GH-003-작업-계층-및-분할-기준.md)를 따른다. Level 3 Issue는 기본적으로 만들지 않는다.

## 3. Workstream과 Repository는 어떻게 구분하나요?

`workstream`은 **일의 기술 영역**이고 Repository는 **Issue를 저장하는 위치**다. Repository 이름에서 Workstream을 자동으로 정하지 않는다.

| 값 | 선택 기준 |
|---|---|
| `BE` | 백엔드 애플리케이션·데이터 구현이 주된 작업 |
| `FE` | 프론트엔드 화면·상태·통신 구현이 주된 작업 |
| `DOCS` | 제품·기술·운영 문서 자체의 작성·정합성이 주된 작업 |
| `INFRA` | 배포·실행 환경·운영 기반이 주된 작업 |

| 예시 | Repository | `workstream` | 이유 |
|---|---|---|---|
| BE·FE를 포함한 가격 차트 L1 | Docs | 비움 가능 | 상위 기능이 여러 영역을 묶음 |
| 가격 조회 API L2 | Backend | `BE` | 백엔드 구현 |
| 백엔드 배포 환경 L2 | Backend | `INFRA` | 인프라 성격의 백엔드 변경 |
| 공통 운영 정책 문서 L2 | Docs | `DOCS` | 문서 자체가 결과물 |

`INFRA`는 별도 인프라 Repository를 뜻하지 않는다. Frontend 배포 작업은 Frontend에, 백엔드 배포 작업은 Backend에 둔다. 자세한 저장 위치와 분할 기준은 [GH-003 작업 분할 가이드](GH-003-작업-계층-및-분할-기준.md)를 따른다.

## 4. Status는 언제 바꾸나요?

Status는 **Project에서 보는 진행 단계**다. Issue의 Open/Closed는 Issue가 열려 있는지 닫혔는지를 뜻하므로 별도로 확인한다.

| 값 | 운영 의미 |
|---|---|
| `Backlog` | 범위·우선순위 또는 착수 조건을 더 정리할 일 |
| `Todo` | 착수 조건과 완료 기준이 정리되어 대기 중인 일 |
| `In Progress` | 담당자가 구현·작성·검증을 진행 중인 일 |
| `In Review` | 결과물에 대한 리뷰·검증 또는 병합 판단 중인 일 |
| `Done` | 해당 Level의 완료 기준을 충족한 일 |

PR이 병합됐더라도 Issue의 완료 조건이 남았다면 `Done`으로 판단하지 않는다. 상태를 바꾸는 순서와 자동화 확인은 [GH-005 Project 사용 가이드](GH-005-프로젝트-뷰-및-자동화-정책.md)를 참고한다. L1의 완료 조건은 [GH-003](GH-003-작업-계층-및-분할-기준.md)에 있다.

## 5. Priority와 날짜는 언제 입력하나요?

Priority는 **무엇을 먼저 처리할지** 정할 때 사용한다. Status나 버그 심각도, 마감일을 대신하지 않는다.

| 값 | 선택 기준 |
|---|---|
| `Urgent` | 현재 장애 또는 출시 차단 조건으로 즉시 판단·처리가 필요한 일 |
| `High` | 현재 목표를 완료하는 데 필수이며 다른 작업보다 먼저 처리할 일 |
| `Medium` | 현재 계획에 포함된 일반적인 순서의 일 |
| `Low` | 연기 가능하고 현재 목표를 막지 않는 일 |

`Urgent`는 실제 장애나 출시 차단처럼 즉시 판단해야 할 때 쓴다. 단순히 오래 열려 있었다는 이유로 선택하지 않는다. 표의 네 값은 **POLICY**이며 GitHub에 등록된 실제 옵션은 **NOT VERIFIED**다. 고정 응답 시간이나 SLA를 뜻하지 않는다.

`Start date`는 계획한 착수일, `Target date`는 계획한 완료 목표일이다. 일정 관리가 필요한 Issue에 입력하며, 단지 Issue 생성일을 복사하지 않는다. 둘 다 입력했다면 목표일은 착수일보다 빠르지 않게 한다. 계획이 달라지면 날짜를 수정하고 변경 이유를 Issue에 남긴다. 실제 완료 시각이나 검증 결과를 날짜 필드로 대체하지 않는다.

## 6. 자주 헷갈리는 조합과 변경 관리

| 혼동하기 쉬운 선택 | 올바른 판단 |
|---|---|
| Docs의 가격 차트 L1이므로 `DOCS` | BE·FE를 함께 포함한다면 Workstream을 비워둘 수 있음 |
| Backend Repository의 배포 작업이므로 `BE` | 배포·실행 환경 작업이면 `INFRA` |
| `Feature` Issue를 만들었으므로 Docs PR에 `type: Feature` | Issue Type과 PR Label은 각각 작업·변경 목적에 따라 선택 |
| PR을 병합했으므로 L1 `Done` | 모든 필수 L2와 L1 인수 조건을 따로 확인 |

필드 이름·옵션·관리 위치를 바꾸기 전에 기존 Issue와 Project 필터·View·자동화에 미치는 영향을 확인하고 사용자 승인을 받는다. 변경 후 실제 GitHub 값과 관련 GH 문서를 대조한다. Priority·Status·Level을 표현하려고 중복 라벨을 만들지 않는다. Priority의 실제 옵션과 날짜 입력 동작은 사용할 때 확인하며, 조회하지 못한 동작을 검증 완료로 기록하지 않는다.
