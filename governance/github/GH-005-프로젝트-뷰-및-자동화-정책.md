# GH-005 — 프로젝트 뷰 및 자동화 정책

- **버전:** V1
- **상태:** 승인
- **적용 범위:** today-fish Organization의 통합 GitHub Project #1
- **실제 설정 확인일:** 2026-11-13
- **관련 문서:** [GH-001 필드 정책](GH-001-이슈-분류-및-필드-정책.md), [GH-002 라벨 정책](GH-002-저장소별-라벨-정책.md), [GH-003 작업 분할 기준](GH-003-작업-계층-및-분할-기준.md), [GH-004 Issue 작성 가이드](GH-004-이슈-템플릿-및-작성-기준.md)

## 핵심 요약

[통합 Project #1](https://github.com/orgs/today-fish/projects/1)에서 작업을 찾고 진행 상태를 관리한다. **View는 Project에 등록된 항목을 필터와 표시 방식에 따라 보여주는 화면**이다. `All Task`에서 전체를 찾고, `Backend`·`Frontend`에서 L2 진행 상황, `MVP Roadmap`에서 L1 목표를 확인한다. 특정 View에 Issue가 없으면 Project 등록 여부와 필터용 필드를 순서대로 확인한다.

## 1. 현재 Project에는 어떤 View가 있나요?

읽기 전용 GitHub 조회에서 Project #1의 실제 제목은 `오늘의 수산-MVP Development`였다. 기존 안내에서 쓰던 `오늘의 수산 — MVP Development`와 띄어쓰기·대시가 다르다. 아래 표는 **현재 표시명과 필터(VERIFIED)**를 적는다. View 이름 자체를 이번 단계에서 바꾸지 않는다.

| 실제 View | 표시 방식 | 실제 필터 | 그룹 기준 | 사용 목적 |
|---|---|---|---|---|
| `All Task` | Table | 없음 | 없음 | Project에 등록된 전체 작업 확인 |
| `Backend` | Board | `is:issue level:L2 workstream:BE` | `Status` 세로 그룹 | 백엔드 L2 진행 관리 |
| `Frontend` | Board | `is:issue level:L2 workstream:FE` | `Status` 세로 그룹 | 프론트엔드 L2 진행 관리 |
| `MVP Roadmap` | Roadmap | `level:L1` | 없음 | L1 목표와 일정 확인 |
| `Maintenance` | Table | `is:issue label:Maintenance` | 없음 | 유지보수 Issue 확인 |

기존 설계에서 부르던 `All Tasks`·`Backend Board`·`Frontend Board`의 실제 표시명은 `All Task`·`Backend`·`Frontend`다. 이 가이드에서는 실제 화면 이름을 쓴다. Board는 Status별 열에서 **L2 진행 단계**를 보고, Roadmap은 **L1 목표의 흐름**을 확인하는 용도다. Roadmap의 세부 표시 필드와 날짜 렌더링 방식은 `NOT VERIFIED`다.

`Maintenance` View는 실제 `Maintenance` 라벨이 있는 Issue만 표시한다. Docs에는 이 라벨이 없으므로 Docs 유지보수 Issue가 이 View에 나타난다고 기대하지 않는다. 새 라벨이나 View를 임의로 추가하지 않는다.

## 2. 필드 이름을 확인하고 작업을 찾기

Project 필드의 실제 표시명을 확인했다. Type은 Project의 별도 필드가 아니라 Organization Issue Type이다. 아래는 설정 확인 결과이며 값의 선택 기준은 [GH-001 필드 선택 가이드](GH-001-이슈-분류-및-필드-정책.md)에 있다.

| 개념 | 실제 확인된 표시명·값 | 확인 범위 |
|---|---|---|
| Type | Organization Issue Type `Feature`·`Task`·`Bug` | GH-001의 조회 결과; Project 필드 아님 |
| Level | `Level`: `L1`·`L2` | VERIFIED |
| Workstream | `workstream`: `BE`·`FE`·`DOCS`·`INFRA` | VERIFIED; 소문자 필드명 유지 |
| Status | `Status`: `Backlog`·`Todo`·`In Progress`·`In Review`·`Done` | VERIFIED |
| Priority | `우선순위` | Issue Field 연결은 VERIFIED, 옵션 `Urgent`·`High`·`Medium`·`Low`의 실제 등록 여부는 NOT VERIFIED |
| Start date·Target date | 같은 이름의 필드 | Issue Field 연결은 VERIFIED, 실제 입력·연동 동작은 NOT VERIFIED |

`Effort`도 Project에 표시되고 Issue Field로 연결돼 있지만, 옵션·운영 의미는 정해지지 않았다. 임의로 점수나 완료 기준으로 사용하지 않는다.

Project에 들어간 뒤 다음 순서로 찾는다.

1. **전체 작업 찾기 — `All Task`:** 제목·Repository·Status로 작업을 찾는다. 전체 View에 없다면 먼저 Project 등록 여부를 확인한다. 필터가 비어 있어도 Project 밖의 모든 GitHub Issue가 자동 표시되는 것은 아니다.
2. **백엔드 진행 — `Backend`:** `L2`이면서 `workstream=BE`인 Issue만 본다. Status 열에서 대기·진행·리뷰·완료를 확인하고 현재 단계에 맞게 상태를 바꾼다. 백엔드 Repository의 `INFRA` 작업은 이 필터에 들어오지 않는다.
3. **프론트엔드 진행 — `Frontend`:** `L2`이면서 `workstream=FE`인 Issue를 관리한다. Frontend Repository에 있는 `INFRA` 작업도 이 View에 자동 포함되지 않는다.
4. **상위 일정 — `MVP Roadmap`:** `L1` 목표의 계획 날짜와 하위 작업 상황을 확인한다. 실제 Roadmap의 표시 필드·날짜 렌더링 방식은 이번 조회에서 검증하지 못했다. L2가 Done이라고 L1을 바로 Done으로 바꾸지 않는다.
5. **완료 후 유지보수 — `Maintenance`:** Backend·Frontend의 `Maintenance` 라벨이 붙은 Issue를 찾는다. 원본 L1과의 관계는 Issue 링크로 확인한다. Docs 유지보수는 이 View에 나타난다고 가정하지 않는다.

View는 필터된 **보기**다. Board에서 보이지 않는 Issue라도 먼저 `All Task`에서 검색한다. 거기에도 없으면 해당 Repository의 Issue가 Project에 등록됐는지 확인한다. Issue 생성과 본문 작성은 [GH-004 Issue 작성 가이드](GH-004-이슈-템플릿-및-작성-기준.md)를 따른다.

## 3. Status와 일정은 어떻게 관리하나요?

| Status | 이렇게 사용할 때 | 직접 확인할 것 |
|---|---|---|
| `Backlog` | 범위·우선순위·착수 조건을 정리 중 | 필요한 기준 문서와 의존 작업 |
| `Todo` | 완료 기준이 정리돼 착수 대기 | 담당자와 선행 조건 |
| `In Progress` | 구현·작성·검증을 진행 | 진행 중 결과와 차단 요인 |
| `In Review` | PR 또는 결과물을 검토 | 리뷰·검증 결과 |
| `Done` | 해당 Level의 완료 기준을 충족 | L2 결과 또는 L1 전체 인수 기준 |

현재 작업 단계가 달라졌다면 Project 항목의 `Status` 값을 위 표에 맞게 변경하고, 원본 Issue의 Open/Closed도 따로 확인한다. PR 병합, Issue Closed, Project Done은 같은 사건이 아니다. L1 완료 요건은 [GH-003 L1/L2 완료 기준](GH-003-작업-계층-및-분할-기준.md)을 따른다.

일정이 필요한 Issue에는 계획 착수일을 `Start date`, 목표일을 `Target date`에 기록한다. `우선순위`는 먼저 처리할 일을 구분할 때 쓴다. 두 날짜 필드와 `우선순위`의 **Issue Field 연결은 VERIFIED**지만, Priority의 실제 옵션과 날짜 입력·연동 동작은 **NOT VERIFIED**다. 따라서 정책값을 실제 화면 선택지로 단정하지 말고 입력 시 확인한다.

## 4. 자동화가 예상과 다르면 무엇을 확인하나요?

실제 Project에는 다음 Workflow가 **활성화된 이름으로 조회됐다(VERIFIED)**: `Auto-add sub-issues to project`, `Auto-add to project`, `Auto-close issue`, `Item added to project`, `Item closed`, `Pull request linked to issue`, `Pull request merged`. 이번 조회로는 각 Workflow의 트리거 상세, 필터, 상태 변경 대상·값, 실행 성공 여부를 알 수 없었다(`NOT VERIFIED`). 이름만으로 자동 결과를 약속하지 않는다.

| 사건 | 수동 확인과 조치 |
|---|---|
| Issue 생성 | Project에 항목이 있는지 확인한다. 없으면 권한 범위에서 통합 Project에 등록한다. |
| 작업 착수 | `Level`·`workstream`·`Status`를 확인하고 실제 단계로 바꾼다. |
| PR 생성·리뷰 | Issue와 PR 연결을 확인하고 `In Review`가 맞는지 본다. |
| PR 병합·Issue 종료 | 병합 결과, Issue Closed 여부, Project `Done`을 각각 확인한다. 누락된 상태만 바로잡는다. |
| L2 완료 | L1의 필수 L2와 상위 인수 기준을 별도로 검증한다. L1 자동 완료를 전제하지 않는다. |

예를 들어 PR을 병합했는데 Project Status가 `Done`이 아니라면 PR의 병합 결과, 연결된 Issue의 상태, Project 항목의 Status를 각각 확인한다. 완료 조건이 충족됐다면 누락된 상태를 수동으로 바로잡는다. Workflow가 **활성화됨**과 해당 Issue에서 **원하는 결과로 실행됨**은 별개다. 전체 작업 순서는 [GH-006 Issue·PR 작업 흐름](GH-006-이슈-PR-생명주기-및-변경-관리.md)을 따른다.

## 5. Board나 Maintenance View에 안 보인다면?

| 증상 | 확인 순서 | 조치 |
|---|---|---|
| `Backend` View에 Issue가 없음 | `All Task`에서 Project 등록 → Issue 여부 → `Level=L2` → `workstream=BE` | 누락된 등록·필드를 바로잡고 View를 다시 확인한다. |
| 잘못된 Workstream | 실제 작업 성격과 변경 Repository를 각각 확인 | [GH-001](GH-001-이슈-분류-및-필드-정책.md)에 맞게 필드를 수정한다. Repository 이름만으로 추론하지 않는다. |
| Status가 자동으로 안 바뀜 | PR·Issue 연결, 병합·종료 상태, 실제 Project Status | 현재 단계에 맞게 수동 수정하고 Workflow 동작을 별도 검증 항목으로 남긴다. |
| Maintenance View에 없음 | Project 등록 → Issue의 `Maintenance` 라벨 → 실제 Repository | Backend·Frontend는 정확한 라벨을 적용한다. Docs에는 현재 라벨이 없으므로 이 View에 표시되지 않는다. |

## 6. 설정을 다시 조회할 때

다음은 읽기 전용 확인 예시다. `gh project field-list`는 일부 Issue Field 옵션을 반환하지 않으므로 빈 옵션을 **값이 없음**으로 단정하지 않는다. View 필터·그룹과 Workflow 이름·활성 여부는 Project GraphQL 조회로 확인했다. Workflow 동작은 실제 이벤트별 확인이 더 필요하다.

```bash
gh project list --owner today-fish --format json
gh project field-list 1 --owner today-fish --format json
gh project view 1 --owner today-fish --format json
```

읽기 권한이나 API 응답이 달라지면 당시 확인 범위를 기록하고, 미조회 항목을 `NOT VERIFIED`로 남긴다. 필드·View·Workflow 설정 변경은 이번 가이드의 수행 범위가 아니다.
