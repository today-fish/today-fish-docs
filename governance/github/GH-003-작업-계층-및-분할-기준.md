# GH-003 — 작업 계층 및 분할 기준

- **버전:** V1
- **상태:** 승인
- **적용 범위:** today-fish MVP와 후속 버전의 GitHub Issue 작업 분해
- **관련 문서:** [GH-001 필드 선택 가이드](GH-001-이슈-분류-및-필드-정책.md), [GH-004 Issue 작성 가이드](GH-004-이슈-템플릿-및-작성-기준.md), [GH-006 작업 흐름 가이드](GH-006-이슈-PR-생명주기-및-변경-관리.md)

## 핵심 결론

기능 전체나 독립 기술 목표를 관리하려면 Docs에 **L1 Issue**를 만든다. 실제로 구현하고 검증할 일은 변경 대상 Repository의 **L2 Issue**로 나눈다. Parent Issue는 상위 목표, Sub-issue는 그 목표에 필요한 실행 작업이다. 단, Repository 간 Parent/Sub-issue 연결 동작은 아직 확인하지 못했다. 연결 전에도 Issue 본문 링크로 관계를 남긴다.

## 1. L1이 필요한가요, L2 하나면 되나요?

| 구분 | L1 — 상위 목표 | L2 — 실행 작업 |
|---|---|---|
| 목적 | 사용자 가치 또는 독립적인 기술 목표를 완성한다. | 목표에 필요한 구현·문서·검증 결과를 만든다. |
| 저장 위치 | Docs Repository의 Parent Issue | 실제 변경 대상인 Docs·Backend·Frontend Repository |
| 범위 | 포함·제외 범위와 기능 전체 완료 기준 | 하나의 명확한 변경 목적과 검증 가능한 결과 |
| 연결 | 필요한 L2와 선행 조건을 모은다. | 관련 L1과 기준 문서·선행 작업을 참조한다. |
| 완료 | 필수 L2 결과와 L1 인수 조건을 함께 확인한다. | 변경·검증·리뷰 근거를 확인한다. |

L1은 보통 `Feature`이지만 독립 기술 목표라면 `Task`도 가능하다. L2는 보통 `Task`이고 결함 수정은 `Bug`가 될 수 있다. Type은 **일의 종류**, Level은 **계층**이므로 Type만으로 Level을 정하지 않는다. 실제 필드 선택은 [GH-001 필드 선택 가이드](GH-001-이슈-분류-및-필드-정책.md)를 따른다.

### L1을 만들 때 확인할 것

1. 기능 또는 기술 목표가 무엇을 제공하는지 한 문장으로 설명할 수 있어야 한다.
2. 포함·제외 범위, 관련 승인 문서, 사용자 또는 운영 관점의 완료 기준을 기록한다.
3. BE·FE·INFRA·DOCS가 함께 필요할 수 있다. 여러 영역을 포함하는 L1의 Workstream은 비워둘 수 있으며 Docs Repository에 있다는 이유로 `DOCS`로 지정하지 않는다.
4. L2가 하나여도 독립 목표의 범위·인수 기준을 별도로 추적할 이유가 있을 때만 L1을 둔다. 단순 작업 하나를 형식 때문에 상위 Issue로 감싸지 않는다.

### L2로 나눌 때 확인할 것

1. 구현 또는 검증 결과가 독립적으로 확인되고 PR에서 리뷰 가능한 크기여야 한다.
2. 대상 Repository, Workstream, 관련 L1, 기준 문서의 절, 완료 조건 및 필요한 테스트를 기록한다.
3. 원칙적으로 L2 Issue 하나에 PR 하나를 연결한다. 변경 목적이 분리되면 L2를 나누고, 같은 목적의 작은 구현 단계는 체크리스트로 묶는다.
4. 체크리스트 항목을 Level 3 Issue로 만들지 않는다. 별도 리뷰·검증이 필요해지면 새 L2로 분리한다.

## 2. 가격 차트 기능을 L1과 L2로 나누기

다음은 실제 등록된 Issue가 아닌 **가상 분할 예시**다. 승인된 가격 차트 요구사항의 실제 절과 완료 조건은 Issue 작성 시 연결한다.

1. **상위 목표 정하기:** 사용자가 품목과 기간을 골라 가격 흐름을 확인한다는 목표를 한 문장으로 쓴다. Docs에 `Feature`·`L1`을 만들고 포함·제외 범위와 화면·데이터 인수 조건을 적는다. BE와 FE를 함께 포함하므로 Workstream은 비워둘 수 있다.
2. **백엔드 결과 나누기:** 가격 조회 API를 Backend의 `Task`·`L2`·`BE`로 만든다. 승인된 응답 계약, 입력·데이터 없음 처리와 검증 방법을 완료 조건으로 적는다.
3. **프론트엔드 결과 나누기:** 차트 표시·기간 선택을 Frontend의 `Task`·`L2`·`FE`로 만든다. UX 상태와 API 응답 연동을 검증한다. 화면과 연동을 독립적으로 리뷰해야 한다면 L2를 더 나눌 수 있다.
4. **관계 확인하기:** 각 L2에 L1 링크와 기준 문서의 정확한 절을 남긴다. FE 검증에 API 응답이 필요하면 BE Issue를 선행 작업으로 링크한다.
5. **완료 확인하기:** L2의 PR·검증 결과를 확인한 뒤 L1 자체의 차트 동작과 인수 조건을 확인한다. L2 완료만으로 L1을 자동 종료하지 않는다.

Issue 본문을 실제로 작성할 때는 [GH-004의 복사용 예시](GH-004-이슈-템플릿-및-작성-기준.md)를 사용한다.

## 3. L2가 너무 크거나 작다면?

PR 크기를 코드 줄 수나 개발 일수의 고정 기준으로 판단하지 않는다. 목적의 응집도, 독립 테스트 가능성, 리뷰 가능성, 선행 작업과의 결합도, 되돌리기 및 장애 영향 범위를 함께 본다.

| 상황 | 처리 |
|---|---|
| 하나의 L2가 서로 다른 계약·저장소·검증 결과를 포함 | 각각 완료 가능한 L2로 분리 |
| 여러 L2가 같은 목적의 작은 순차 편집만 반복 | 하나의 L2와 체크리스트로 통합 |
| 선행 작업의 결과가 있어야 착수 또는 검증 가능 | 선행 Issue를 링크하고 차단 조건을 명시 |
| 병렬로 진행해도 독립 검증 가능한 BE·FE 작업 | 별도 L2로 두고 공통 L1에 연결 |

예를 들어 가격 조회 API와 차트 화면을 하나의 L2로 묶었다면 Repository와 검증 결과가 다르므로 나눈다. 반대로 같은 API의 작은 DTO 정리와 입력 검증이 하나의 결과를 만들고 함께 리뷰된다면 한 L2의 체크리스트로 둔다.

의존관계는 Issue 링크와 본문의 선행·후행 설명으로 추적한다. Project에 새 의존 필드나 라벨을 추가하지 않는다. 선행 작업이 끝나야 검증할 수 있다면 무엇을 기다리는지 명시한다.

## 4. 다른 기능에도 같은 기준을 적용하기

다음은 Issue를 생성한 기록이 아니라 [PF-005 실시간 채팅 요구사항](../../MVP/product/features/PF-005-실시간-채팅.md)을 기준으로 한 분할 예시다. 가격 차트와 마찬가지로 결과·검증 단위가 다르면 별도 L2로 둔다.

| 예시 Issue | 위치·필드 | 확인할 결과 |
|---|---|---|
| L1 품목별 실시간 채팅 제공 | Docs; `Feature`, `L1`; BE·FE를 포함하므로 Workstream 비움 | 참여·전송·실패 UX와 성능 인수 조건 충족 |
| L2 STOMP 참여·복원 계약 구현 | Backend; `Task`, `L2`, `BE` | 인증된 참여·복원과 오류 응답을 독립 검증 |
| L2 채팅 연결·재연결 구현 | Frontend; `Task`, `L2`, `FE` | 최초 연결·재연결·연결 유지 동작을 검증 |
| L2 채팅 화면 상태 구현 | Frontend; `Task`, `L2`, `FE` | 패널과 정상·대기·오류 상태를 검증 |
| L2 WebSocket 운영 환경 검증 | Backend; `Task`, `L2`, `INFRA` | 실제 배포 경로와 연결 조건을 검증 |

각 L2에는 L1과 관련 제품·UX·ADR·Tech Spec의 정확한 절을 연결한다. PR에는 해당 L2와 검증 근거를 연결한다. GitHub의 Repository 간 Parent/Sub-issue 관계가 실제로 사용 가능한지는 Issue 작성 단계에서 확인한다(`NOT VERIFIED`). 확인 전에도 상위 L1 링크를 본문에 남긴다.

## 5. INFRA Issue는 어디에 만드나요?

`INFRA`는 Workstream이며 별도 Repository가 아니다. 백엔드 배포·DB 등은 Backend Repository, 프론트엔드 배포 등은 Frontend Repository, 공통 운영 정책 문서 자체는 Docs Repository에 Issue를 둔다. Repository는 실제 변경 대상, Workstream은 작업 성격으로 선택한다.

## 6. 언제 완료하고 범위를 바꾸나요?

| 대상 | 완료 기준 |
|---|---|
| L2 | 합의한 결과물이 반영되고 테스트·문서 검증 증빙이 남아 있으며 관련 PR의 리뷰·병합 판단이 끝남 |
| L1 | 필수 L2가 완료되고 상위 범위·인수 기준을 확인했으며 남은 필수 작업이 없음 |

결과를 구현하지 않았거나 검증하지 않았다면 완료로 기록하지 않는다. 실행 순서와 Project Status 확인은 [GH-006 작업 흐름 가이드](GH-006-이슈-PR-생명주기-및-변경-관리.md)에 있다.

범위가 바뀌면 원본 요구사항과 L1의 포함·제외 범위, 관련 L2의 완료 조건 및 의존관계를 먼저 대조한다. 별도 사용자 가치나 독립 완료 기준이 생기면 새 L1로, 기존 목표 안에서 분리 검증이 필요하면 새 L2로 관리한다.

### 완료된 L1에서 새 Bug가 생겼다면?

완료된 L1에서 나중에 발생한 버그·개선·리팩터링은 신규 Issue로 관리한다. L2 성격이어도 기존 L1의 Sub-issue로 추가하지 않고 관련 Issue 링크로 원본 맥락을 남긴다. 이로써 최초 개발 L1의 완료 판정과 진행률을 유지한다. 다만 원래 인수 기준을 실제로 충족하지 못했거나 잘못 닫은 경우에는 해당 L1을 재오픈해 바로잡을 수 있다.

Backend·Frontend의 신규 유지보수 Issue에는 기존 `Maintenance` 라벨을 지정하고 필요한 `scope: *`를 함께 사용한다. Docs Repository에는 현재 `Maintenance` 라벨이 없다. Docs 유지보수의 Issue Type은 일의 종류로 정하고, 관련 Docs PR은 기존 `type: *`·`area: *` 규칙으로 분류한다. Docs에도 `Maintenance`를 추가할지는 별도 결정 사항이며 이 문서가 새 라벨을 생성하지 않는다.
